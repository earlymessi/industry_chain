## 1. 建议定位

建议在现有统一侧边栏增加一级入口「运维资源调度」，作为与订单调度并行的业务入口；首期先做一个工作台页面，通过页内标签承接完整流程。

这里的“运维”按设备、产线和物流资产的巡检、保养、检修、故障恢复理解。服务器、容器和网络等 IT 运维暂不纳入首期范围。

核心定位是：**由资源健康和维护需求产生任务，安排维修人员、备件、工具、运输与停机窗口，再评估并协调生产计划。**

两类需求共用资源，却保留不同的业务含义：

| 对比项 | 订单驱动 | 运维驱动 |
|---|---|---|
| 起点 | 客户订单、生产任务、交期 | 故障、巡检异常、保养到期、维修请求 |
| 调度对象 | 加工工序、加工机器、生产物流 | 检修任务、维修人员、备件工具、维修物流、设备窗口 |
| 主要目标 | 按期交付、生产效率、成本 | 恢复能力、及时维护、减少停机和资源冲突 |
| 订单的作用 | 主要调度需求 | 生产占用、重要度和延误代价的来源 |
| 没有生产订单时 | 无订单排程需求 | 仍可巡检、生成保养任务、调度和执行维修 |

不要求用户先建一个“生产订单”才能创建检修任务。生产任务与维护任务在资源层协调，在业务层分别管理。

以下为根据当前代码进行的静态分析；只有停机窗口重叠问题补做了不写文件、不连接数据库的最小内存验证。

| 当前能力 | 可复用部分 | 集成需要补充的内容 |

| JSSP 排程与停机配置 | 机台维护日历、`downtime_blocks`、候选机台 | 完整区间冲突校验、发布后持续约束 |
| 故障事件重排 | 基准甘特、剩余任务重排、R0/R1/R2 影响分析 | 与真实检修进度衔接、在制品处置、恢复确认 |
| 计划停机事件 | 输入多个设备停机区间并计算影响 | 使用实际执行基线、冻结已开工工序、预览与发布分离 |

| 物料与供应模块 | 库存、缺料、在途与供应商信息 | 备件分类、维修适配、预留、领用和退料 |
| 厂内 AGV | 从生产甘特生成搬运任务、分配车辆 | 从运维任务生成备件/工具配送任务 |
| 多周期车辆路径模块 | 多地点、时间窗、路网与路线优化基础 | 现场服务任务、维修技能、服务时长和业务标识适配 |
| 数字孪生、报表、助手 | 设备/人员/AGV 展示、解释和导航 | 运维状态与事件来源、运维指标和工具能力 |

### 2.1 不能直接按“已经具备”处理的边界

1. **设备健康目前依赖排程结果。** 当前页面主要从甘特计算连续工作超限，并导出 PDF，不是传感器健康诊断，也不是完整维护工单系统。
2. **维护单闭环尚未建立。** 主后端声明了 `maintenance_orders` 集合引用，但本次查看范围内未发现配套的任务创建、派工、执行、验收流程。
3. **机台停机约束存在区间重叠风险。** 最小内存验证中，维护窗口为 `[3,5)`，一项从时刻 1 开始、时长 4 的工序仍得到 `[1,5)` 的安排。当前通用模型只检查开始时刻是否位于窗口内；后续实现必须检查整个工序区间，不能仅增加前端提示。
4. **计划停机函数不能原样用于执行中场景。** 当前该函数重新计算前后方案，未复用故障分支的冻结剩余工序流程，不能保证维持真实执行基线。
5. **现有事件执行链可能同步写回 MES。** 新页面的“预览”必须调用明确无写入的评估路径，不能把现有执行接口直接当预览接口。
6. **当前 MES 为单个 active 执行记录。** 首期以一个现场、一个活动生产计划为协调范围。工厂级多计划并行协调属于后续扩展。
7. **子系统共用菜单不等于共用调度约束。** Scheduletool、MASA-QMIX 与车辆路径模块尚不能默认共享机台、人员、时间单位和资源占用。

## 3. 优先适配场景

| 场景 | 触发与资源需求 | 与现有系统的衔接 | 建议阶段 |
|---|---|---|---|
| 计划性保养 | 日历到期、累计运行小时达到阈值；需要技工、备件、工具与维护窗口 | 使用生产空隙安排窗口，计算交期影响，发布设备不可用区间 | 首期 |
| 故障抢修 | 人工报修、停机事件；需要诊断、维修、配送和复机检验 | 关联故障事件，安排维修资源，评估订单受影响程度 | 首期 |
| 巡检异常处理 | 巡检发现异响、泄漏、松动等；需要检查或预防处理 | 无订单也能建任务；有生产时提供不停机检查或停机处理方案 | 首期，先人工录入 |
| 维修延期与恢复 | 缺件、维修超时、复机检验不通过 | 延长停机区间，重新安排维修和剩余生产任务 | 首期必须覆盖 |
| AGV 保养、补能与替换 | 车辆不可用或达到维护阈值 | 更新车辆可用窗口，调整厂内配送任务 | 第二期 |
| 备件紧急补给 | 备件不足、在途延误、外协维修 | 连接库存和供应商状态，生成运维配送需求 | 第二期 |
| 多站点上门运维 | 不同地点的巡检和维修；技工、车辆、服务时间窗 | 适配车辆路径模块，结合人员技能及工作班次 | 第三期 |
| 基于状态的预测性维护 | 真实运行数据、趋势与故障历史 | 在资产和执行数据可信后引入风险模型 | 后续研究 |

首期推荐选“设备保养 + 故障抢修 + 巡检异常”三个场景。它们与当前制造系统的资源和生产影响联系最紧密，也能在没有现场传感器的情况下形成可验收闭环。

阈值规则产生的是维护建议或负荷预警，不直接标为“故障预测”。

## 4. 新页面的组织方式

### 4.1 入口与现有菜单关系

建议入口名称为「运维资源调度」，前端建议路径为 `/new-ui/home/operations`。

- 「生产资源管控」继续承接订单、加工排程和生产执行。
- 「运维资源调度」承接维护需求、维修资源安排、执行和恢复。
- 原「设备健康管控」保留为生产侧分析入口，点击“创建维护任务”时带入资产、风险与来源，跳转新页面。
- 「物流资源管控」继续承接车辆路径能力，运维任务按需发起路线优化；不再复制一套车辆实验页面。
- 产业链主控台汇总运维造成的产能风险与待恢复资源，具体处理仍回到运维工作台。

### 4.2 一个工作台，五个页内标签

| 标签 | 展示内容 | 核心操作 |
|---|---|---|
| 运维总览 | 待处理任务、停机设备、维修资源缺口、当日维护安排、数字孪生状态 | 人工报修、查看影响、进入待办 |
| 事件与任务 | 故障、巡检、保养需求和维护任务，支持任务依赖与来源追溯 | 确认事件、生成任务、调整优先级 |
| 资源与窗口 | 技工班次、维修工具、备件、设备可用区间及生产占用 | 查询缺口、准备资源、选择维护时间窗 |
| 调度与影响 | 运维甘特、生产甘特、备件到位与方案对比 | 生成预案、评估、修改、确认发布 |
| 执行与复盘 | 到场、领料、维修、检验、验收、延期和关闭 | 更新进度、申请延长、验收复机、查看履历 |

调度页重点回答五个问题：先修哪台、谁去修、何时能修、资源是否齐备、会影响哪些生产任务。

页面顶部始终显示现场、时间范围、真实/仿真模式、当前执行计划、资源快照时间和预案状态。“未绑定生产计划”不阻止维护任务创建和资源调度。

## 5. 业务闭环与状态规则

建议主流程：事件进入 → 确认需求 → 建立维护任务 → 检查资源 → 生成预案 → 生产影响评估 → 确认发布 → 执行维修 → 检验验收 → 释放资源并更新生产。

### 5.1 三类状态分别管理

| 对象 | 建议状态与含义 |
|---|---|
| 运维事件 | 新建、已确认、处理中、已解决、已关闭；重复告警可关联同一个事件 |
| 维护任务 | 草稿、待资源、待调度、已安排、执行中、待验收、已完成、已取消；缺件/受阻作为附带原因记录 |
| 调度方案 | 草稿、计算中、可行、不可行、待发布、已发布、已失效、被替代 |

“预案可行”不代表已派工，“维修结束”不代表已允许生产，“预计恢复时间已到”不代表设备自动恢复。

### 5.2 计划保养与故障抢修采取不同策略

- 计划保养优先搜索生产空闲窗口，可在允许的维护期限内调整；不可中断的加工工序不因保养建议被直接打断。
- 故障报修一经确认设备不可用，应立即形成资源不可用事实；即使还没有维修人员，也不能继续把设备排成可用。
- 故障发生在加工中时，需要明确在制品的继续加工、剩余加工、重做或报废策略，不能把已开始工序简单当作已完成。
- 抢修预计时长未知时，记录估计范围和下次复核时刻；不得因估计结束时间到达而自动解除不可用状态。
- 检验通过后，由确认的恢复事件更新可用区间；是否优化后续生产计划再次单独评估。

## 6. 调度方法：先建立可靠约束，再扩展联合优化

### 6.1 首期采用分层协调

第一层安排运维任务：选择维修人员、必要工具、备件、配送和维护窗口。

第二层评估生产：把候选窗口转换为机台不可用区间，结合当前执行快照、生产占用与交期，调用生产重排和影响评估能力。

第三层调整候选：若生产影响超出阈值，尝试其他窗口、维修班组、外协方案或分批保养，再比较结果。

有限次迭代后仍不满足要求时，返回不可行原因和可放宽项，不生成看似完整但资源冲突的方案。分层方法的优势是容易复用现有系统，但不能宣称实现跨生产、维修、物流的全局最优。

### 6.2 约束与目标

必须满足的约束包括：

- 同一人员、独占工具、设备在同一时段不能被重复占用；多人维修任务需同时具备所需技能组合。
- 作业时间属于允许班次；跨日班次、休息和已发布占用必须参与可用性计算。
- 维护作业及必要的隔离、试机区间，与不允许并行的生产工序不重叠。
- 需要的备件在开工前到位且已预留；“当前有库存”不等于未被其他任务预占。
- 前置诊断、配送、拆卸、维修、检验之间满足依赖关系；设备仅在验收后恢复可用。
- 已完成作业固定；已开始作业按不可中断或明确的中断策略处理；已发布任务的变动需可追溯。

优化目标建议按层级处理：先保证可行和强制处置要求，再减少关键设备恢复时间与维护超期，之后权衡订单加权延期、停机时长、维修负荷、运输成本与计划扰动。不要用一个很大的权重代替必须满足的硬约束。

首期采用“关键度与时限排序 + 技能匹配 + 可用窗口搜索 + 局部调整”，能逐步解释每项安排的原因。现有 TS/GA 等算法可用于适配后的生产子问题；不能默认现有 JSSP 求解器已支持多技能维修和备件库存约束。

### 6.3 比较口径

计划保养至少比较“保留当前生产计划、另选维护窗口”“当前窗口保养、仅做必要顺延”“当前窗口保养并重排剩余生产”三种方案。

故障抢修可沿用 R0/R1/R2 语言，但明确：R0 是事件前的对比基线，故障确认后已不可执行；R1 是采取必要停机与顺延、未做优化；R2 是满足运维资源约束后的维修安排与生产重排。

所有方案来自同一资源和执行快照，使用相同时间尺度及业务指标，才能比较。

## 7. 与现有系统的具体集成

| 集成位置 | 读取与复用 | 发布后的联动 | 首期限制 |
|---|---|---|---|
| 设备健康 | 风险对象、阈值、生产负荷 | 创建关联维护事件与任务 | 风险分析搬到可复用后端服务，避免只存在于页面 |
| 生产排程 | 当前执行甘特、工单、交期、候选机台 | 维护占用进入资源日历，确认后同步选定生产方案 | 先补完整区间校验和执行冻结 |
| 人员管控 | 同一人员身份、在岗信息 | 维修派工和生产派工共同检查时间占用 | 另补维修技能与资质，不能把“会操作机台”视为“会维修” |
| 物料与外协 | 库存、供应商、备件到货信息 | 预留、领用、退料、补给请求 | 备件与生产原料分类型管理，现有供应演示需补库存流水适配 |
| 厂内 AGV | 车辆、位置、现有配送能力 | 生成维修备件/工具配送，关联维护任务 | 现有生产甘特提取器需新增运维任务输入 |
| 物流车辆路径 | 地点、服务时间、车辆路线计算能力 | 输出多站点运维访问顺序 | 后续适配；不是直接把维修任务当作当前客户 CSV |
| 组装与供应链 | 工位映射、产能风险、物料就绪 | 先展示影响；适配后同步受影响资源窗口 | 未接入约束的引擎显示“仅影响提示”，不声称联合重排 |
| 数字孪生 | 同一机台、人员、车辆身份与位置 | 增加故障、待修、维修中、试机和恢复状态 | 演示状态与真实状态分开标记 |
| 报表与知识库 | 当前影响分析、维修文档与助手 | 复盘维修过程、查手册与生成说明 | 手册回答不自动变成现场操作指令 |

### 7.1 共享资源事实，而不是只共享页面

每种资源保留一个权威身份。生产机台、组装工位、车辆和人员通过映射表关联，而不是按名称猜测相同资产。

增加统一资源占用服务，记录已发布的生产、维护、物流占用及容量。旧模块在最终派工或发布前也要查询它；只让新页面查询、旧页面绕过查询，仍会重复派工。

一个机台维护窗口发布后，后续新订单排程和再次优化必须继续读取它；不能仅在本次重排请求里临时携带窗口，刷新页面后就丢失约束。

### 7.2 保留独立上下文

现有 `useWorkContextStore` 表示当前生产计划。新页面另设运维任务/方案上下文，通过关联计划 ID 引用生产计划，避免选择一个维修任务就覆盖用户当前的订单上下文。

一次维护可以关联多个受影响订单，但首期只有一个活动 MES 执行计划参与自动协调。未执行计划可以标记风险和重新计算需求，暂不自动批量覆盖。

### 7.3 助手作为辅助入口

后续可增加运维领域 Agent，复用现有编排器和确定性工具层。典型请求如“给 M3 安排两小时保养，并比较对今天交付的影响”。

助手负责理解需求、补齐参数、查维修知识和解释方案；人员选择、库存校验、时间窗验证由服务计算。助手与页面调用同一套运维服务。预览不能派工、不能扣库存、不能更新 MES。

## 8. 建议数据与接口契约

下列对象和接口均为拟新增或拟扩展内容，不表示当前已经存在。

### 8.1 关键数据对象

| 对象 | 核心字段与作用 |
|---|---|
| 资产与映射 | 全局 `asset_id`、资源类型、所属现场、原模块 ID、重要度、可用状态、状态来源、版本 |
| 运维事件 | `event_id`、来源、资产、事件类型、发生/接收时间、严重度、重复合并标识、确认人 |
| 维护任务 | `maintenance_order_id`、关联事件、维修步骤、时长估计、技能人数、备件工具、前置任务、最晚完成时间、停机要求、状态和版本 |
| 资源日历与预留 | 资源 ID、容量、时间区间、占用来源、发布版本、有效状态、预留到期时间 |
| 运维调度方案 | `scenario_id`、来源任务、资源/库存/执行快照版本、候选安排、可行性、影响指标、选中方案、发布状态 |
| 执行与验收记录 | 实际开完工、领退料、维修结果、试机、验收人、恢复时刻、延期原因 |
| 发布事件记录 | `publication_id`、幂等键、待同步目标、处理状态、重试与错误记录 |

原则上沿用 MongoDB；`maintenance_orders` 的使用方式应在实施前统一，避免新旧同名对象含义不同。生产加工任务与维修任务不混用同一个工艺字段结构。

### 8.2 时间和数据来源

- 业务记录保存带时区的绝对时间；页面按 Asia/Shanghai 展示。调度运算使用明确的时间原点和单位。
- 当前 MES 使用相对小时，车辆路径使用分钟。必须有显式适配器；还需验证生产任务构造中的整数工时取整，避免 30 分钟检修被静默缩短或改变。
- 真实运维时间与 MES 演示时钟分别记录，不能混用。仿真任务只影响对应仿真资源日历。
- 已观测、人工录入、规则推算、算法预测分别标记，便于判断一个“预计恢复时刻”是否有现场反馈支撑。

### 8.3 建议接口职责

| 接口族 | 建议职责 |
|---|---|
| `/api/operations/events` | 报修、巡检异常、事件确认和合并 |
| `/api/operations/orders` | 维护任务、步骤、资源需求和状态流转 |
| `/api/operations/resources` | 资源可用性、占用、备件缺口与映射 |
| `/api/operations/scenarios` | 异步生成、查询预案和影响；默认无业务写入 |
| `/api/operations/scenarios/{id}/publish` | 校验快照版本、幂等发布、预留和派工 |
| `/api/operations/orders/{id}/execution` | 记录进度、受阻、延期和实际资源使用 |
| `/api/operations/orders/{id}/acceptance` | 验收、确认恢复、释放占用和归档 |

## 9. 预览、发布与异常处理

### 9.1 发布流程

1. 固化资产状态、人员占用、备件库存、活动生产计划和仿真时刻的快照，生成方案。
2. 展示安排、资源缺口、交期变化、变更清单和不可行原因，允许调整后重新计算。
3. 用户选择方案并确认发布。
4. 服务端检查方案依赖的版本是否变化，重新做硬约束校验。快照过期则拒绝发布并提示重新评估。
5. 以同一发布标识建立人员/工具/备件预留和资源窗口，记录待同步事件。
6. 同步派工、配送以及用户确认采用的生产方案，记录各目标的处理结果。
7. 确认完成或显示“部分同步、待恢复”，不以一个接口返回成功掩盖后续同步失败。

对于真正需要停机的故障，设备不可用事实不等到这套发布流程完成才生效；发布流程主要决定维修安排及采用哪套协调方案。

### 9.2 一致性和恢复

本项目通常使用本机 MongoDB，不能默认部署支持多文档事务。方案应支持版本条件更新、可幂等的库存流水和预留记录、持久化待处理事件与补偿；若部署为支持事务的副本集，再在适当范围使用事务。

重复点击发布不得重复扣减/预留库存、重复派工或创建多份配送任务。同步失败后重试仍使用同一业务标识。

已开始的维修或已经领出的备件不能简单“回滚删除”。撤销应形成新版本，说明哪些预留可以释放、哪些实际发生记录必须保留；设备继续停机与否由真实状态决定。

多个异常连续发生时，在最新资源状态上滚动评估，合并同一资产的有效不可用区间，避免后一次预案覆盖前一次未完成维修。

## 10. 一个可演示的完整场景

以下数字仅作业务演示，不是实测优化结果。

设 M3 已达到保养阈值，需要 2 小时保养、1 名具备机械维修技能的人员、1 套工具和1 个备件。工厂当天有正在执行的订单。

1. 设备健康页显示规则预警，用户确认创建维护任务；任务关联 M3 和预警来源，生产计划仅作为影响上下文。
2. 运维工作台检查到维修员甲上午有生产占用、维修员乙下午在岗，工具可用，备件 13:00 才到位。
3. 系统生成候选：13:30 开始、15:00 开始、次日允许窗口；排除技能冲突、备件未到和跨越不可中断工序的安排。
4. 对可行候选评估停机时长、维护超期、订单延期和计划扰动，展示每项指标，不预设哪个方案一定更优。
5. 用户选择 15:00—17:00 的保养方案，确认后预留维修员乙、工具和备件，并发布设备窗口。若另一个用户已占用乙，版本校验失败，返回重新评估。
6. 厂内物流按需配送备件，执行人员记录开始、领料和维修进展。
7. 若发现额外损坏，任务延长并触发协调预案；原定 17:00 不自动复机。
8. 维修完成后进入试机与验收，验收通过才释放设备不可用状态，并重新评估剩余生产安排。
9. 实际停机、等待备件、人工工时、影响订单和改进建议归档到设备履历。

若当时没有生产订单，同一流程仍可安排维修人员、工具、备件和设备窗口，生产影响显示“当前无活动生产计划”。

## 11. 分阶段实施范围

| 阶段 | 交付内容 | 完成条件 |
|---|---|---|
| 前置验证 | 资产/人员映射、时间转换、整段停机冲突校验、执行冻结、无写入预览契约 | 已识别边界均有针对性验收结果 |
| 第一期：厂内维护闭环 | 一个运维工作台；报修/巡检/保养；维护任务；技能班次；基础备件预留；窗口调度；生产影响；发布；执行验收 | 有订单和无订单均可闭环，资源不重复占用 |
| 第二期：跨资源联动 | 运维配送、外协备件、AGV 不可用窗口、主控台与数字孪生、助手入口 | 任务与配送、领料、资源状态可追溯且同步可恢复 |
| 第三期：多站点与高级优化 | 维修车辆路线、跨现场资源、多个活动计划、历史时长估计 | 各子系统约束适配通过，再评估联合优化效果 |

首期不新增独立 Flask 服务，不另建一套账号、人员和设备主数据，也不要求更换现有生产算法。新增运维业务服务及资源协调能力，通过现有 FastAPI 统一提供接口；跨模块长期约束需要逐步补齐。

## 12. 验收方案与评价指标

### 12.1 必须通过的业务用例

| 用例 | 验收结果 |
|---|---|
| 无订单安排设备保养 | 能创建、调度、发布、执行、验收，不要求伪造生产计划 |
| 生产任务跨入检修时段 | 不可中断工序的整个区间不得与检修区间重叠 |
| 执行中安排计划保养 | 已完成部分不变，已开始部分遵守中断策略，实际基线不被重新计算替换 |
| 同一技工同时参与生产和维修 | 统一占用校验能识别冲突，至少一侧安排被阻止或调整 |
| 同一备件被两个方案使用 | 预览可比较，最终发布只能预留可用数量 |
| 故障维修时间不确定 | 未验收前不因预计结束时刻到达而恢复设备 |
| 用户仅预览方案 | 不修改 MES、不派工、不产生正式库存预留 |
| 重复发布和并发修改 | 幂等且不覆盖更新后的资源/执行状态 |
| 发布期间一个模块同步失败 | 显示未完成目标，可恢复重试，不形成虚假全成功 |
| 刷新页面和后端重启 | 已发布占用、维护任务和执行记录仍可恢复 |
| 维修延期或验收不通过 | 资源继续不可用，影响评估使用最新事实 |
| 不同时间单位与模式 | 小时/分钟转换、跨日班次、真实/仿真隔离通过明确样例 |
| 子模块未完成适配 | 明确展示“仅影响提示”，不将其结果标成已满足统一资源约束 |

### 12.2 指标口径

- **可行性指标**：已发布方案的资源冲突数、备件超预留数、非法跨停机工序数应为 0。
- **维修指标**：首次响应时间、维修历时、停机历时、等待备件时长、维护按期完成率。分别记录确认、到场、维修、验收时间，避免混淆口径。
- **协调指标**：受影响订单数、加权延期、生产计划调整量、维修人员负荷和运维运输距离。
- **运行指标**：预案计算时长、发布成功率、同步失败恢复率、重复发布去重结果。

效果应在相同任务、资源快照和实际约束下，与人工/先到先服务基线比较。未积累故障历史时，不宣称降低故障率或提高 OEE 的具体百分比。

## 13. 实施前需要确认的业务信息

本稿按厂内设备运维优先设计。进入开发前需确定：首批资产与关键度、维修专业和班次、典型保养步骤及工时、备件工具清单、实际资产编码映射、生产工序中断规则、验收与恢复责任人、是否有真实状态数据、真实与演示时钟的使用方式。

这些信息可以先用小范围样例补齐，再扩展到全部设备。现阶段不需要为了演示独立运维调度而先接入 IoT 或训练新模型。
