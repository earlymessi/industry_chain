日期：2026-11-10。对应[开发计划](产业链运维系统开发计划.md)。本次交付的是能持续执行并处理约束变化的统一模拟运行首版，尚不具备现场生产系统上线所需的全部条件。

**基线对齐修复：**当前已改为原系统同源基线，旧独立两加工中心示例已归档。使用原生产计划44工序、原组装9工序18工位和原物流车辆14/路线0，合计93任务27资源；可直接选择已保存生产计划导入，缺下游关联则标未绑定。批量、BOM和日历等标准关联参数仍须业务确认。详见[基线对齐修复记录](产业链运维基线对齐修复记录.md)。下方早期小模型指标保留为历史机制验收，不代表新基线规模。

**生产库内同步更新：**默认从「生产来源」选择任意库内已排程计划与算法，不再自动启用固定演示计划。每15秒检查来源变化，预览后同步同源未开工任务，保留已执行进度、本地确认修改和既有下游关联；另一份计划或工艺结构变化须明确归档后启用。最新回归 **519 passed、20 skipped、0 failed**，新增9项同步测试；前端6项检查、生产构建和空/活动组件渲染通过。8008实测10份已排程来源可选，当前93任务实例完成同源绑定同步，运行ID、原计划日期及下游定义保持。记录：`.integration/operations-production-sync-acceptance.json`。

此前基线对齐修复验证为 **510 passed、20 skipped、0 failed**，8008实际接口14项检查通过。旧独立实例及历史已保留；原计划、旧MES和实际库存没有被新模块覆盖。

## 1. 现在可以怎么操作

1. 按[部署启动](部署启动.md)启动 MongoDB 和 `tests/main.py`，打开主系统。
2. 点击侧边栏 **产业链运维系统**，或访问 `http://127.0.0.1:8008/new-ui/home/operations-tools`。
3. 首次点击「选择已排程计划」，选择库内计划和已保存算法，预览校验后启用。之后进入读取原实例；通过「生产来源」检查并同步库内更新，不重新初始化。标准演示仅作手动备用。
4. 顶部查看生产、物料、组装、配送，点击环节筛选计划；中间切换「实时 · 4h / 今日 / 7天 / 4周」，分别查看工序、当日、日汇总、周汇总，点击日期查看任务。页面关闭后后台继续。
5. 右侧「运维操作」直接选择环节、机台故障/工时调整/到货延期等操作、具体对象和新参数，然后「确认变化」。点击资源或任务会直接带入对象。备注、预约和 AI 辅助默认折叠。
6. 点击「生成调整计划」，在抽屉查看推荐候选及原/新安排，再「应用此计划」。详细算法、校验和不可行原因按需展开。等待期间继续执行。
7. 故障抢修结束点击该资源「确认恢复」，运行与调整记录从顶部「记录」查看。

页面简化更新：主页面收敛为四环节、可切换粒度的计划、固定运维操作台；取消原四个内容标签和大段说明。六项前端时间/汇总测试通过，验证北京时间边界、跨日占用、粒度与环节筛选、远期数据缺口、实际/预测区别及超期阻塞任务仍可处理。空状态及活动计划组件渲染检查通过；实际屏幕交互仍受下述工具限制。

AI 输入例如「Machine-0 故障，预计20分钟恢复」，只产生待核对草稿；不会把“预计恢复”误当作已经复机。需要具体排程时输入「分析当前影响并生成调整方案」，调用相同求解工具。LLM 未配置时工具链仍可用。

## 2. 数据从哪里来，结果是什么

当前数据为 `data/operations/standard/production_source.json` 和 `binding.json`。标准模拟保留原12个部件工单的44道工序，将显式关联的同批部件送入原18工位、9工序组装，再承接已保存物流路线的两个客户、5件需求。原生产工时以小时转换为秒，未按单件再乘批量，缺少客户承诺保持空值。完整来源和新增假设在页面「来源与关联」可核对。

后台把服务器当前时间、已发布安排、可用资源、物料数量和事件结合，产生任务开工/完成、剩余工作、阻塞、物料流转与模拟到货。物料不足、资源未复机、工艺前置未完成、车辆未返场或不满足客户硬窗口时不会仅因时间走到便算完成。

输出包括当前状态、剩余任务具体安排、组装就绪时间、车辆访问顺序、客户交付预测、延期与调整记录。不能可靠预测的订单显示待评估。初始承诺单独保存，确认后的承诺变更有记录。没有成本输入，不给“零成本最优”结论。

现有生产计划可选择具体算法、确认单位后导入未开工仿真副本，保持原甘特。缺组装/配送关联时对应环节标未绑定；原BOM或客户承诺缺失也明确展示。完整统一 JSON 仍可导入，未宣称自动接管各模块当前现场状态。

## 4. 求解和校验依据

生产候选使用已有 TS 内核以及 EDD/SPT；搜索评分与输出甘特共用修复后的解码。生产顺序最终仍交给统一协调器，纳入当前在制、班次、物料、组装与配送约束。TS 内部局部目标不被当作最终履约最优证明。

组装使用原工序和允许工位集合，采用确定性派工；配送继承保存的运输批次、车辆、容量、访问前缀与路段，按来源区分软/硬窗口。没有强行调用不匹配的 QMIX，也未宣称运行完整 MO-ALNS。当前原路线仅授权车辆14，缺失时不会凭空补造备用车或拆批。

一次正常搜索最多比较基准加27项生产/组装/路线策略组合，去重后最多返回3项。硬约束独立检查覆盖漏排/重复、能力、工时、前置、完整日历、占用、库存、车辆、装载、路线时间、硬窗口、冻结实际及滚动窗口外安排。无法验证则不可应用。

即时事件按秒生效；近端默认4小时，必要时24小时或7天；窗口外安排与预留保持，冲突要扩大窗口。超7天形成4周能力请求，不给整月细排。页面汇总仅覆盖已经导入的日历和需求，不将远期未给定解释为产能充足。

## 5. 验证记录

测试环境：Windows，本仓库当前 Python 环境，MongoDB 本机实例；前端 Vite 生产构建。规模为标准三订单/十九任务及既有仓库回归，不作为3000任务或多工厂并发性能承诺。

自动化检查包括统一链完成且库存不重复扣减、故障只中断受影响工作、预计恢复不自动复机、剩余单件工时修正、供给阻塞、迟报不回拨、幂等和维护权转移、窗口外冻结、四周请求、六类标准变化、未完成交付不误报、API 慢求解不停钟和旧候选拒绝。完整测试命令：

```powershell
python -m pytest tests -q --tb=short
cd frontend
npm run build
```

初次全量回归发现现有车辆路径依赖 `folium` 未安装，造成10项旧测试失败；补齐 requirements.txt 已声明的依赖后旧模块测试恢复。最终通过数量以本节下方最新命令结果为准。

最终全量结果：**499 passed、20 skipped、0 failed**，本次约9.37秒，包含32项新增运维测试；20项跳过沿用既有测试条件，不能算作执行通过。两项既有警告涉及 Starlette WSGI 与 NumPy matlib 弃用。前端生产构建成功并输出到 `tests/templates/dist`；保留既有第三方注解及 jsPDF 混合导入警告。

主系统8008已启动并核验运维健康状态 online、页面及入口脚本200、车辆路径模块 mounted=true。临时8009验收服务已停止，隔离验收数据保留用于复核。

**独立三订单基准：**`tests/operations/test_reference_benchmark.py` 以独立分钟运算穷举生产、组装、配送各6种顺序，共216组合。复核原顺序总延期50分钟，参考最优总延期0、最早返场距起点175分钟，达到双目标的组合2项。当前有界候选搜索在此算例达到0延期；线上次目标优先减少改动，因此没有把参考的最早返场目标偷换成线上最优结论。此结果只对该限定小例子成立。

**真实时钟和 Mongo 验收：**在与主库隔离的 `*_operations_verify` 数据库、8009临时服务进行，未向主库灌入故障。12项断言通过：服务重启保留同一实例与原计划日期、追赶当前时间、四层汇总、维修预计到点不复机、无页面情况下其他任务继续、独立求解、候选校验、应用重校验、过程时钟连续、重复应用409、无LLM工具轨迹、SSE当前快照。

原始开发验收日志位于本地 `.integration/operations-acceptance.json` 与 `.integration/operations-full-pytest.log`，属开发产物；本文件保存可阅读的结果。

**页面验收限制：**计算机使用工具因无法可靠识别 Windows 当前浏览器 URL 而停止，未继续界面操作。已验证页面路由和资源可由主后端提供、前端构建通过；尚未完成点击操作、屏幕布局、响应式与重连提示的实际浏览器检查，不能将HTTP验收称为完整UI验收。

## 6. 系统/Agent 带来的具体变化

原来各环节独立模拟，需要人工对齐时间、数量和就绪信息；现在标准计划在同一实例连续运行，故障对生产、组装、配送的影响按同一关系传播。

原来一句“调整任务顺序”需要人再排一遍；现在输出具体任务、资源、起止、车辆访问和逐项校验。AI 负责把已知对象和参数整理成草稿、说明影响并调用确定性工具，计划可执行性由统一计算与独立校验决定。没有模型也能完成闭环。

本阶段可以证明的是功能闭环与给定输入下的约束一致性。实际减少多少延期、人工处理时间或成本，需要导入真实基线、事件和指标并进行对照评估，本次不预填提升百分比。

## 7. 下一阶段

先做人工页面验收；再针对真实业务选定订单→生产批次→组装成品→配送的正式ID、单位和状态来源，逐个补适配器。现场模式还需实际反馈采集、权限和审计身份、质量及在制工艺约束、部署监控与备份恢复演练。算法侧补代表规模、多种子、可行率/目标差距/时延评估，达到约定指标后再扩大适用范围。
