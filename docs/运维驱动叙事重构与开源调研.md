# 运维驱动叙事重构与开源调研

日期：2026-11-07。本文为定位评审与方案论证，不涉及应用代码修改。

2026-11-10 设计更新：当前方案采用服务器当前时间驱动已发布计划，前序映射未具备时先运行完整标准计划；故障事件即时进入，后台分层计算未来调整，主时钟不停。生产计划优先适配，其余前序模块按映射完成度逐项接入。参数、具体排程和可靠性校验见[产业链运维系统设计方案最新版](产业链运维系统设计方案.md)。本文保留此前论证，冲突内容以新版为准。

## 1. 本次重新判断

原《运维驱动资源调度系统集成方案》以厂内设备的保养、报修和维修恢复为主，作为厂内维护闭环设计有价值；若与“订单产运优化—生产排程—组装排程—配送调度”的产业链履约主线并列，则业务粒度没有对齐。

原系统已经在生产排程之后，通过生产看板模拟 MES 执行并处理动态异常。若新增运维页面仍主要重复“机台故障—生产重排—比较交期”，新增内容会集中在维修工单和资源检查上，难以形成独立的产业链级调度叙事。

因此，需要先重定运维驱动的业务对象与调度范围，再讨论页面和接口集成。增加关联 ID、统一菜单和状态联动，能够改善集成，但不能单独解决层级错位。

建议的系统定位为：

**订单履约与运维保障双需求驱动的产业链分布式资源适配与协同调度。**

- 订单履约驱动：响应产品需求，配置制造、组装、采购及配送能力。
- 运维保障驱动：响应资产健康、维修与服务时限需求，配置跨节点服务人员、备件、工具、运输及外部维修能力。
- 两类主线共享资源事实与局部调度能力，分别管理需求、执行过程和评价目标。

## 2. 三个层级必须分清

| 层级 | 订单履约视角 | 运维保障视角 |
|---|---|---|
| 产业链业务层 | 一批产品如何按要求完成制造与交付 | 多个产业链节点的资源能力如何维持和恢复 |
| 跨节点协调层 | 订单分配、产运协同、组装衔接、交付安排 | 维护优先级、服务商匹配、备件来源、跨站人员与运输协同 |
| 局部执行层 | 具体车间排程、组装求解、车辆路线、MES 异常重排 | 具体维修任务安排、人员路线、备件配送、验收与能力恢复 |

现有生产看板的动态重排属于局部执行层。产业链运维保障的输出可以引起它运行，但运维主线本身不应围绕反复调用同一生产重排流程展开。

两条主线不必都经过全部原有子系统。资源复用按实际需要发生：有现成备件时调拨配送即可；缺少专用件时才产生备件采购或制造子需求；维护改变当前产能时才评估相应生产计划。

## 3. 运维范围的三个选择

| 选择 | 业务范围 | 与当前系统的关系 | 本次建议 |
|---|---|---|---|
| 厂内设备维护 | 一个工厂的设备、技工、备件与维护窗口 | 与设备健康和 MES 故障重排紧密相连 | 保留为运维执行子场景 |
| 产业链节点共享运维服务 | 零部件厂、加工厂、总装厂等节点，通过共享服务站、备件库和外部服务商恢复设备能力 | 能保持现有制造产业链主题，并产生跨节点资源竞争 | 作为新主线的首选定位 |
| 在役产品与装备的服务网络 | OEM 为分布在客户现场的已交付装备提供维修、备件和工程师服务 | 可连接制造交付后的全生命周期，但需要新增在役资产和服务合同等模型 | 后续扩展方向 |

首版推荐选择“产业链节点共享运维服务”。例如，以现有冰箱产业链为背景，研究加工节点和组装节点共享的维修服务与备件保障，而不是立即扩展到全部消费者售后。

多地点并不自动等于产业链协同。应同时具备：节点归属和地点可区分、资源需求可跨节点匹配、存在共享资源竞争或互补、能够表达节点能力变化对其他节点的影响。仅在地图上放多个故障点，仍不足以体现这类协调。

## 4. 建议的新业务主线

主流程建议为：

**资源状态进入 → 保障需求形成 → 节点影响评估 → 分布式资源匹配 → 人员/备件/运输协同 → 维修与验收 → 资源能力更新。**

### 4.1 独立业务对象

新主线的核心对象是“运维保障需求”，至少包含：

- 需求来自哪个节点、哪个资产或资产组，状态证据是什么。
- 属于故障处置、预防维护、检验校准或恢复性服务。
- 所需专业技能、人员数量、工具、备件及适配条件。
- 可服务时间窗、目标恢复时间、服务时限和允许的替代方式。
- 资源不可用或降级后，损失哪些能力，哪些下游节点受到影响。
- 可接受的服务商、备件来源、运输方式与授权范围。

它可以在没有当前产品订单时成立，例如例行维护或恢复关键设备可用性。存在生产订单时，订单延期和在制品影响作为协调代价进入评估，不改变运维需求本身的业务身份。

### 4.2 与旧主线的区别

| 对比项 | 订单履约驱动 | 运维保障驱动 |
|---|---|---|
| 主要输入 | 产品、数量、工艺、交期 | 资产状态、维护要求、服务时限、能力损失 |
| 主要匹配 | 生产任务与制造/组装/配送资源 | 维护需求与工程师/备件/工具/运输/服务商 |
| 核心协调 | 哪些节点生产，何时生产和交付 | 先保障哪里，资源从哪里来，何时恢复能力 |
| 典型输出 | 生产与配送计划 | 跨节点运维保障方案与恢复能力时间表 |
| 核心指标 | 产品延期、生产成本、负荷与效率 | 服务超时、加权不可用时间、恢复覆盖、保障成本 |
| 原生产排程的角色 | 主体计算能力之一 | 按需复用的局部执行或影响评估能力 |

评价运维方案时，不能只把原订单交期权重换个名称。需要显式考虑服务时限、跨节点移动、人料同步到位、备件适配、资源独占、班次与维护步骤依赖。

## 5. 一个体现产业链分布式资源的场景

以下为建议的演示场景，不代表当前已有现场数据或接口。

设零部件加工节点 A、总装节点 B、共享运维服务站 H 和外部服务商 E 构成一个协作网络。A 的设备状态影响向 B 提供关键零件的能力。H 有有限的专业工程师和工具，两个备件来源的库存与到达时间不同。

1. A 出现需要机械专业工程师和轴承的维护需求；B 同时出现需要同一稀缺工具或部分相同人员的检修需求。
2. 系统检查两处维护时限、现有库存缓冲和节点依赖，判断哪个节点延迟恢复会造成更大的网络影响。
3. 对照本地库存、跨库调拨、外部采购及外部服务商，形成候选资源组合。
4. 联合安排工程师访问顺序、工具占用、备件运输与维修开始时间。工程师先到但备件未到时，应显示等待，不能仍按人员到场时间计算恢复。
5. 比较“自有资源顺序保障”“外包其中一项”“调拨备件并行恢复”等方案，展示时限违约、资源等待、服务成本和节点恢复时间。
6. 发布选定方案后，各节点反馈到场、领料、维修与验收进度；延期触发服务任务重新协调。
7. 资产验收后更新节点资源能力。只有受到能力变化影响的生产/组装任务才进一步评估调整。

这段故事的决策冲突发生在跨节点保障资源分配上。A 的生产看板只负责显示和处理 A 的本地生产影响；它不承担整个运维网络的协调职责。

原订单主线也可以引用同一变化：A 预计恢复延迟，会降低关键零件供应能力，进而影响 B 的组装和订单交付。这样，两条主线通过资源能力事实衔接。

## 6. 需要新增的调度问题

仅复用原生产算法和车辆路径页面，不能自动解决分布式运维。

### 6.1 决策变量

- 每个维护需求由哪个服务站或服务商承接。
- 哪些工程师、工具和备件分配给它。
- 备件从哪个来源提供，是否需要采购或制造。
- 人员和运输任务按什么顺序执行。
- 维修何时开始、何时检验、何时恢复资源能力。

### 6.2 最小同步约束

维修开始时间不能早于以下条件同时满足的时刻：工程师到位、备件到位、工具到位、资产允许维护、前置任务完成。

在此基础上，还需校验技能组合、班次、跨地点移动、备件适配、库存与独占工具占用。多人合作任务需要表达同时到场或分步骤参与，而不是把维修等同于一次普通送货。

### 6.3 目标与方法

首期建议采用确定性的维护时长和关键度，优化加权服务超时/资源不可用时间与总服务成本，保留多个可行方案供比较。没有可靠数据时，不以模型输出一个故障概率代替真实观测。

实现可先采用资源分配与路线/时间安排的分层协调，并在层间反馈到达时间与可行性。该方法可解释、便于扩展，但不预先承诺全局最优。需要保留“资源不足、无可行方案”的结果。

## 8. Agent 的职责与算法边界

建议组织为一条运维保障流程，而不是根据页面数量创建多个 Agent：

- 状态与诊断：归并告警、查询设备记录和手册，整理有证据的维护需求。
- 影响判断：关联资产、节点能力、依赖与服务时限，解释维护优先级。
- 资源协调：识别技能、备件和工具要求，调用确定性匹配与调度工具，比较候选。
- 执行与验证：归集进度、发现偏差、检查验收证据并更新资源能力。

LLM 可以参与信息理解、知识检索、参数补全与方案解释。库存、资格、移动时间、资源冲突、开始/结束时间和恢复状态应由服务与校验器管理。

原六岗助手及生产异常重排仍服务现有订单执行，不要求在每个维护需求上完整重跑原来的订单流程。

## 9. 与当前代码的复用与缺口

| 当前模块 | 新主线可复用的部分 | 必须新增或适配 |
|---|---|---|
| 知识库与 Agent Harness | 手册检索、工具执行、上下文、追踪 | 运维领域对象、诊断证据和保障任务工具 |
| 外协供应商 | 供应方与在途状态的展示基础 | 维修服务能力、备件适配、库存来源、资源预留和报价时限 |
| 多周期车辆路径 | 地点、路网、车辆与多周期路线计算基础 | 服务任务输入、工程师技能、维修服务时间与人料同步约束 |
| 人员调度 | 人员身份、在岗信息 | 服务站归属、维修技能、跨站班次、移动与占用日历 |
| 生产策略工作台 | 局部生产方案、约束评估 | 维修需求转备件制造子任务的适配；读取维护资源可用性 |
| MES 动态重排 | 本地执行态、故障影响与重排 | 接收相关资源能力变化，保留当前生产上下文与确认边界 |
| 组装与就绪 | 加工完工到组装输入的既有映射 | 维护造成的能力/预计就绪影响与实际就绪区分 |
| 产业链主控台 | 统一壳层与跨模块状态展示 | 节点—资产—能力—依赖模型，以及运维保障网络视图 |

当前 MES 使用单个 `active` 执行记录，人员派工主要针对在岗生产机台，车辆路径模块使用独立客户订单模型。这些都不能直接视为多个企业节点已经统一共享资源和执行状态。

因此，目前能够复用相当一部分交互、工具和局部计算基础，但分布式运维的资源模型、任务模型和协调约束属于新增核心工作。

## 10. 页面叙事建议

在业务概念上区分两种视角：

- **订单履约**：围绕产品批次，查看订单产运、生产、组装和配送。
- **运维保障**：围绕资源网络，查看节点状态、保障需求、资源分布、协调预案、执行恢复。

根据“原有系统已经开发完成，不推翻重做”的约束，首期在现有侧边栏新增「产业链运维工具」，不要求重组主控台或增加全局模式切换。建议路径为 `/new-ui/home/operations-tools`。

工具页以“场景与需求”“服务资源”“协同方案”“执行推演”四个页内标签承接主要过程，呈现跨节点资源分配、人员和备件到达时间、服务等待与能力恢复。

点击某节点后再进入其生产看板、组装评估或局部维修详情；不在运维页面复制第二套 APS、组装排程和生产 MES。

## 11. 可实现性与最小验证范围

**可实现产业链分布式运维的可验证原型，现有代码尚不具备直接启用这一能力的完整条件。**

最小验证建议包含：

1. 两个有明确归属和地点的受保障节点，并表达至少一种物料或能力依赖。
2. 一个共享服务站与一个外部服务选项。
3. 至少两项存在人员或工具竞争的维护需求。
4. 两个有不同库存与到达时间的备件来源。
5. 一次“局部优先选择”与“跨节点协调选择”会产生不同结果的对照。
6. 一次维修延期后的重新协调，以及验收后资源能力的更新。
7. 对主工厂的一项实际生产影响适配；其他尚未接入的节点显式使用模拟状态，不能伪称真实跨企业运行。

首期可以让当前工厂继续使用已有 MES，新增外部节点的模拟状态与服务任务执行器，不强行让单个 active 记录同时模拟多个工厂。要实现多个真实现场并行运行，后续需扩展站点和执行实例模型，接入资源数据与可用的业务接口。

若没有跨节点可共享或可替代的资源、没有可验证的协同决策，则范围应明确称为厂内维护。后续定位是否覆盖跨企业、区域售后或在役装备服务，应根据资源和数据条件逐步扩展。

## 12. 对旧方案的处理建议

原方案中的停机窗口校验、人员/备件预留、预览发布分离、执行验收和异常恢复仍有价值，应作为“厂内执行适配与维护任务闭环”的内容保留。

其顶层定位、首期场景、页面结构、Agent 分工及验收主线需要根据本论证重写。应先确定分布式运维保障模型和最小跨节点场景，再据此形成新的实施方案，避免继续以厂内故障重排作为新系统的主要叙事。

## 13. 交付约束：新增侧边工具，保留现有系统

本节根据后续用户要求确定增量实施边界，作为首期交付范围。前述产业链运维定位不意味着需要重新开发原有订单系统。

### 13.1 首期接入范围

| 范围 | 建议实现 |
|---|---|
| 现有前端壳层 | 增加一个侧边菜单、一个路由及对应页面标题，沿用现有布局 |
| 运维页面 | 新增独立工具页与页内标签，不重做订单、生产、组装或物流页面 |
| 运维服务 | 在现有 FastAPI 下挂载独立的 `/api/operations-tools/*` 接口组 |
| 运维数据 | 绑定原主线的统一场景基线；维护服务资源、保障需求、预案和推演分支使用独立集合保存，并引用同一基线标识 |
| 原有业务 | 保持现有订单流程、生产算法、MES 动态重排、组装和配送入口的既有行为 |
| Agent | 首期在工具内部使用运维分析与工具调用能力，不要求重构原六岗助手路由 |

因此，应用层只需要少量入口接线，主要开发量集中于新增的运维工具及其调度模型。

### 13.2 首期业务能力

首期定位为跨节点运维保障方案与推演工具，独立支持两个以上节点的维护需求、专用维修服务资源、备件来源、跨节点运输、候选方案比较、执行推演和恢复记录。

新增的服务节点可先人工维护，模拟数据应明确标记。调度结果包括服务站/服务商选择、工程师安排、备件来源与运输、预计维护开始和恢复时间，以及约束不可满足的原因。独立维护测算可以没有生产排程；本项目首期主线演示必须绑定已选定的订单与排程快照，并评估运维结果对同一批订单的影响。

### 13.3 与原系统的初始连接

初始连接采用“共同基线、分支推演、影响回算”：必须绑定原订单、生产资产、选定排程及相关供应与组装映射的固定版本，保存引用标识、完整快照和统一业务时刻。页面导航用于查看详情，不能代替业务数据关联。对会推进仿真或触发事件的现有状态接口，应通过专用只读适配器获取持久化快照，不能仅凭 GET 方法认定其无写入。

首期主要使用独立的维护服务资源池。原生产人员和库存若仅供参考，不应被展示为已完成实际派工或库存预留。要真正共享同一人员、车辆、库存与设备窗口，需要后续对相应发布入口增加占用、版本和一致性校验。

运维工具中的推演与预案按同一基线的不同分支独立保存。首期应通过新增适配器在副本上调用可复用的生产影响评估与重排能力，将恢复时间回算为原工单完工、零件预计就绪和订单交付风险；缺少组装或配送输入时应标记未评估，不能输出虚构的端到端结果。实际改变当前生产执行仍沿用原有发布与动态重排流程。

### 13.4 后续可选适配

工具运行稳定后，再按需求增加“将确认后的恢复窗口传给现有重排服务”“同步实际资源预留”“在主控台汇总运维风险”等小范围适配。每项适配单独明确写入对象、确认流程和回退边界。

工具级接入可以保持原有核心流程稳定。自动跨模块闭环则需要相应接口与资源占用规则配合，不应承诺只增加一个页面就自动实现。

## 14. 叙事连接的前提：统一基线

根据用户对“运维是否脱离主线”的补充要求，首期不能只完成独立运维算例与页面跳转。两种视角必须共享同一个业务世界：原订单确定需要保障的履约目标，运维协调资源能力恢复，再用原订单的履约结果验证保障价值。

基线至少包含节点与资产、订单与工艺、选定计划、统一时刻的执行状态、库存与在途、生产到组装再到交付的依赖关系；在此之上新增工程师、维修备件、工具、服务站和移动时间。故障作为事件叠加于基线，不能重新生成一套无关订单。

建议采用“冰箱零部件生产—整机组装—交付”的场景，先核对并冻结现有候选计划，再补齐映射和维护资源。详细的数据构成、候选数据核查及后续即时执行与运维设计见[产业链运维系统设计方案](产业链运维系统设计方案.md)。该文档为待实施方案，不代表数据库已生成或业务链路已实现。
