# 产业链计划衔接实施记录

2026-11-11。新增「产业链运维系统 → 计划衔接」，原订单驱动模块及生产看板继续保留。衔接功能建立可追溯的模拟执行计划，不自动接管原MES在制状态，不修改原工单、组装评估、物流结果或实际库存。

## 操作步骤

1. 点击页面顶部「计划衔接」，选择库内生产计划、保存算法、时间单位和计划起点，点击「读取工单，关联部件」。
2. 确认组装数量。选择适用的已保存QMIX结果，或「按原工艺补排」。配送选择已保存路线及明确日期，也可标记暂不绑定。
3. 在「部件与交接」勾选本批需要的生产工单，填写整批产出件数、每台用量及消耗工序；核对外购件用量、可用库存与到货日期。前序未覆盖的到货可添加「补充到货批次」，明确物料、数量和日期，不用虚增现有库存代替未来到货。
4. 确认部件转运、成品交接、装车耗时及资源日历；原组装工艺已有检测调试、打包入库，不重复生成这些工序。独立转运确实不需要时可填0。
5. 勾选核对确认，点击「预览衔接」。查看各环节时间原点、交接任务、具体资源和起止安排，以及原组装甘特发生的时间调整。
6. 「保存配置」可复用本批关联。预览后明确启用；已有运行时按钮为「归档当前运行并启用」，旧进度、事件完整保留。仅预览或保存不会切换实例，也不暂停后台时钟。

## 数据与时间规则

| 环节 | 数据来源 | 时间及衔接方式 |
|---|---|---|
| 生产 | MongoDB work_orders的选定排程及原设备目录 | 明确起点＋原相对甘特×单位；原甘特先校验，衔接不能偷偷改动生产安排 |
| 自制件 | 用户确认的来源工单、件数、每台用量、消耗工序 | 来源工单末工序产生部件库存；一个生产批次不自动当成一件部件 |
| 外购件 | 现有外购件目录、purchased_supply_state库存与待到货批次 | ETA锚定来源快照updated_at，允许明确覆盖实际日期；刷新不重算“现在＋ETA”。已到货不重复叠加库存 |
| 组装 | 原9工序18工位，或选定的适用QMIX甘特 | 补排使用原前置、工位及标准分钟工时；保存结果必须确认时间单位和零点，衔接引起的变动逐项显示 |
| 转运交接 | 运维配置 | 每项整批交接占一个明确作业位，具有输入、输出、工时与前置，能登记故障和调整工时 |
| 配送 | 当前保存的车辆路线、时间线及该日客户需求CSV | 来源第N天显式绑定实际日期，0分钟对应08:00；保留路线车辆、客户数量与路段耗时。客户承诺另填，不能用窗口代替 |

日历需明确选择24小时连续或每日班次，覆盖1—28天。班次容不下原生产甘特则拒绝预览，要求修正日历或先由生产模块确认新排程。启用后固定日期；保存配置的旧起点过期也不会自动平移，须重新确认日期。

配送保留固定发车时刻：装车必须在发车前完成，首段行驶不能推迟发车。提前到达收货点时，等待占用车辆。客户原软窗口及惩罚口径保留，可明确收紧为硬窗口；原窗口不随上游延期平移。「客户收货窗口 / 交付承诺」可补充每个客户的实际承诺日期；未填仍显示待确认。支持终点仓与起点仓不同的原路线，不能强行改成返原仓。

## 校验与运行

- 校验生产来源、唯一部件关系、工单产出件数、组装用量、外购库存/供给、工艺前置、资源日历、占用、车辆容量、客户数量和装载守恒。
- 原生产甘特保持；保存组装结果先校验工序覆盖、工位能力、工艺前置和重叠。合并后按当前约束计算，任何组装时间变化在预览列明。
- 原工艺补排使用现有确定性协调器，根据前置、物料和资源空档给出具体安排，独立校验后才能启用。验证可行性，不宣称联合最优。
- 缺料、无法唯一映射、数量不符、错过固定发车等返回明确原因，不以零耗时或自动平移窗口掩盖。
- 预览5分钟有效。启用时重新读取生产、组装、供给及配送来源指纹；来源已变、活动实例已变或预览过期均要求重做预览。
- 新链路建立后可继续使用原运维事件、实时执行、候选调整和生产同源同步。源生产数量改变须重新确认部件/组装/配送分配，不能只改生产任务数量而保留旧绑定。

## 接口及存储

前缀 `/api/operations-tools`：

| 方法 | 用途 |
|---|---|
| GET /plans/chain/sources | 组装评估、工艺、路线及供给目录 |
| GET /plans/chain/route?route_id=… | 所选路线及客户数量 |
| POST /plans/chain/production | 读取所选生产来源工单，用于明确部件绑定 |
| GET /plans/chain/draft | 读取保存的衔接配置 |
| PUT /plans/chain/draft | 保存配置；不改变执行状态 |
| POST /plans/chain/preview | 确认配置后生成并独立校验全链路，返回preview_id及差异 |
| POST /plans/activate | source=chain、preview_id；已有运行还须confirm_new_run=true及匹配previous_run_id |

配置保存在 `operations_chain_configs`，预览保存在 `operations_previews`，正式执行沿用已有快照、命令、事件及归档机制。原模块业务数据只读。

## 当前范围与验证

当前面向原冰箱组装工艺，一个衔接批次选择一条保存路线；客户需求总量必须等于本批组装数量。跨多产品BOM、部分发运、自动拆批或新路线生成尚未加入，不能用复制旧路线冒充已支持。配送未绑定时明确显示待绑定，不计为完整交付计划。

旧QMIX评估有的仍采用旧多能力工位模型，与当前固定9工序18工位定义不一致。当前支持四列甘特在工位能唯一对应工序时导入，或带明确工序ID的五列甘特；无法可靠映射时拒绝并提示原工艺补排。没有将无关旧结果改名伪装成当前工艺。

本次实际读取36份评估、69条路线、10类外购件。选用库内44道生产工序、5台原工艺补排、两项转运及原路线，完成95任务联合预览；真实接口确认缺料、需求数量不符和错过发车被拒绝，活动实例ID及日期保持，未启用开发测试计划。抽查旧6件QMIX评估因工位能力不兼容被拒绝，按明确边界处理。

验证结果：**528 passed、20 skipped、0 failed**；新增9项衔接测试，包括补充到货、四/五列组装映射、固定发车在实际执行中阻塞、跨仓终点和归档启用。前端6项检查、构建、页面与表单的离线组件渲染通过。测试、构建与接口记录分别位于 `.integration/operations-chain-pytest.log`、`.integration/operations-chain-build.log`、`.integration/operations-chain-acceptance.json`。离线渲染未等同于实际浏览器点击验收。
