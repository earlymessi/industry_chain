## 1. 安装与配置

以下命令在 Windows PowerShell 中执行；未特别说明时，工作目录为项目根目录。

### 1.1 首次安装

完整应用使用 Python 3.10 及以上语法，本机已验证 Python 3.12.7。前端 Vite 8 要求 Node.js `^20.19.0` 或 `>=22.12.0`，本机已验证 Node.js 24.16.0。需要可连接的 MongoDB；模型、向量服务和在线路网计算需要网络。

```powershell
python -m venv .\metaforge-test-env
.\metaforge-test-env\Scripts\python.exe -m pip install setuptools wheel
.\metaforge-test-env\Scripts\python.exe -m pip install -r .\requirements.txt -r .\Scheduletool\requirements.txt -r .\zhenjie\requirements.txt -r .\rag\langchain-agent\requirements.txt flask-cors gym==0.26.2
.\metaforge-test-env\Scripts\python.exe -m pip install -e . --no-build-isolation --no-deps

# 只在文件不存在时复制，不覆盖已有配置。
if (-not (Test-Path .\.env)) { Copy-Item .\.env.example .\.env }
if (-not (Test-Path .\rag\langchain-agent\.env)) {
    Copy-Item .\rag\langchain-agent\.env.example .\rag\langchain-agent\.env
}

cd .\frontend
npm install
npm run build
cd ..
```

前端输出为 `tests/templates/dist/`，由主后端托管。各模块依赖使用同一虚拟环境安装，仅安装项目包不能替代完整依赖安装。

### 1.2 配置文件

根目录 `.env` 的主要配置：

```dotenv
METAFORGE_HOST=127.0.0.1
METAFORGE_PORT=8008
METAFORGE_RELOAD=0
MONGO_URL=mongodb://localhost:27017
MONGO_DB=metaforge_mes
OPERATIONS_ENABLED=1
OPERATIONS_SOLVER_TIMEOUT=30
MASA_QMIX_UI_URL=/masa-qmix/
RAG_STREAMLIT_AUTOSTART=1
RAG_STREAMLIT_PORT=8501
RAG_CHAT_PROVIDER=deepseek
RAG_RETRIEVAL_MODE=keyword
```

使用大模型问答时设置 `LLM_ENABLED=1`，填写有效的 `DEEPSEEK_API_KEY`、`DEEPSEEK_MODEL`、`DEEPSEEK_BASE_URL`；客户端也支持智谱配置。只验证排程与页面时，可设 `LLM_ENABLED=0`、`LLM_ROUTER=rule`、`LLM_FALLBACK=rule`。真实密钥不提交到仓库。

知识库对话与工具调用Agent已统一使用根目录现有DeepSeek配置，`RAG_CHAT_PROVIDER=deepseek` 时，即使存在旧智谱密钥也不会用于对话。DeepSeek对话客户端支持工具调用，显式缺少密钥时会报配置错误。

当前设置 `RAG_RETRIEVAL_MODE=keyword`，使用本地BM25关键词检索；不调用嵌入接口、不下载本地模型。现有向量库仅作为已保存文本片段的只读来源，新增和更新内容写入独立的 `storage/keyword_documents.sqlite3`，支持上传、同步、预览和删除。关键词模式重建只调整本地索引，不删除旧向量库。

知识库另读取 `rag/langchain-agent/.env`。若将来明确切回 `hybrid`，才需要单独配置兼容的嵌入服务；DeepSeek对话密钥不能作为 `embedding-2` 密钥使用。与根目录同名的配置应保持一致，避免继承的空值或旧值遮蔽配置。原始知识文档、索引与清单位置以该模块 `config/chroma.yaml` 的 `data_path`、`persist_directory`、`manifest_store` 为准；向量库可能位于仓库外，备份时须一并覆盖。

主程序读取根 `.env` 并覆盖同名进程环境变量，修改后需重启后端。物流订单默认使用 `zhenjie_vrp` 数据库，可通过 `ZHENJIE_MONGO_URI` 指定连接；子模块连接配置不能仅由主库配置推断。

### 1.3 启动与开发

```powershell
Start-Service MongoDB                             # 已运行可跳过
cd .\tests
..\metaforge-test-env\Scripts\python.exe .\main.py
```

出现 `Application startup complete` 且服务监听8008后，访问 **http://127.0.0.1:8008/go**。启动数据库被拒绝时，先在管理员终端启动 MongoDB；使用其他数据库部署时配置其实际地址。

供应链、组装和物流随主后端挂载，无需分别启动开发服务器。知识库默认尝试启动8501进程；未成功时，另开终端在项目根目录执行 `.\scripts\start_rag_streamlit.ps1`。可用 `RAG_PYTHON` 指定该进程的解释器。

修改前端后执行 `npm run build`；修改后端、配置或依赖后，在原终端按 `Ctrl+C`，退出后重新启动。另开终端进入 `frontend/` 执行 `npm run dev` 可使用 `http://localhost:5173/new-ui/`；默认代理到8008，端口改变时配置 `VITE_API_PROXY`。默认关闭后端热重载，建议单 Uvicorn worker。

后端停止后不会继续执行模拟，恢复后从检查点追赶当前模拟时间。刷新网页不重开案例。

## 3. 业务流程与原系统关系

前序模块确定订单及生产、组装、配送计划，运维模块管理同一批产品执行中的偏差。

| 环节 | 输入 | 输出与衔接 |
|---|---|---|
| 供应链订单调度 | 订单、产能与产运参数 | 订单分配及优化结果；后续仍需核对具体来源与数量 |
| 生产资源管控 | 工单、工艺、设备、算法与约束 | 保存的工序甘特、方案及计划包 |
| 自制件与外购供给 | 生产产出、独立 BOM、采购与库存 | 到货批次、入厂运输及组装齐套条件 |
| 组装资源管控 | 工艺、工位、部件与批量 | 工序安排、甘特及评估结果 |
| 物流资源管控 | 客户需求、车辆、路网与窗口 | 车辆路线、发车与客户时序 |
| 产业链运维智能体 | 经确认的关联计划、执行快照与变化事件 | 影响范围、候选安排、校验及确认应用记录 |

生产模块保留原 MES 仿真、协同策略、计划包和异常重排。全链运维使用独立实例关联前序结果，不直接接管原 MES 在制状态，也不改写原工单、库存或历史。前序缺少的到货、运输及交接信息通过明确配置补齐。

生产、组装、配送各有数据中心。普通历史只有补齐 BOM、来源、数量、运输及时间关系并通过校验后，才能组成完整执行基线。

## 4. 计划衔接、来源同步与案例

### 4.1 配置完整计划

1. 在前序模块计算并保存结果。生产来源必须含已保存甘特，只计算未入库的结果不会进入来源列表。
2. 打开运维“计划配置 → 完整衔接”，选择生产计划、算法、时间单位和起点；多工厂分别确认来源与资源归属。
3. 核对部件产出、每台用量与消耗工序；以独立 BOM 关联自有工厂、供应商、采购单、库存及入厂运输。
4. 选择兼容的组装历史或“按原工艺补排”；选择配送历史/路线，确认需求、产品、仓库、日期、交接与装车时间。
5. 核对日历并预览。规格、单位、数量、版本、库存、工艺、资源和运输时序通过校验后确认启用；已有运行需明确归档再启用。

预览与保存配置不改变当前执行。预览有效期5分钟，启用时重新检查来源指纹，变化或过期后须重做。

| 来源 | 时间映射 |
|---|---|
| 生产 | 确认起点＋原甘特偏移×所选单位；默认与原生产界面一致为小时 |
| 组装 | 原结果零点＋明确单位；补排依据齐套、工艺与工位空档 |
| 外购及厂际运输 | 明确备货、发运、装卸与到货时刻；运输完成才计入收货 |
| 配送 | 原路线日绑定实际日期，零分钟对应08:00；保留路段、服务及客户窗口口径 |

整批产出件数、每台 BOM 用量、组装数量和客户需求分别确认，不把一个工单当成一个部件，不重复计入库存与运输到货。启用后日期固定，刷新不平移；历史复用需明确“整体映射到当前时间”后重新预览。承诺交期与收货窗口分开，未设交期时不宣称已评价延期。

### 4.2 生产来源同步

来源约每15秒检查更新，只提示“库内有更新”，用户预览确认后同步。相同来源及稳定工单/工序结构可同步未开工部分，已开工、已完成和已消耗投入的事实保留。

同步比较上次来源、当前运维值和新来源：仅一方修改时采用相应值，两边冲突则提示处理。故障、库存及进度不复位。更换计划、工序增删或结构变化时归档旧运行并建立新实例；组装与物流整份新结果目前不自动原位同步。

### 4.3 test1、test2、test3

| 名称 | 时间跨度 | 区别 |
|---|---|---|
| test1 | 约2天 | 常规生产与采购后组装配送 |
| test2 | 7天内 | 工厂B第6天启动，外购同周备货 |
| test3 | 4周内 | 工厂B第4周启动，外购当周备货 |

每套均含两家自有工厂、7道生产任务、12项独立 BOM 用料、10份采购单、8趟入厂运输、45道组装及装车/配送/返场，共66项任务、5台成品。跨度来自释放和备货日期，未放大加工或行驶时长。

生产来自原库内 Q 算法保存模板；组装为当前9工序、18工位规则排程，明确标注非 QMIX；配送复用同一份原物流算法实际求解的5台路线版本，分别绑定可发车日期。

在任一数据中心选择同名案例，可查看甘特和任务，复用回原模块，或点击“运维配置”载入完整关联再预览启用。历史预览按当前时间展示保存偏移并标记“预览映射”，不改写历史和活动实例。时间轴可拖动，双击空白恢复跟随当前时间。

其他部署需先具备原生产计划 `693c1376a4c27d96652ad849` 及设备目录，再在根目录运行：

```powershell
.\metaforge-test-env\Scripts\python.exe .\scripts\seed_chain_examples.py
```

脚本维护三套测试来源及配套历史，不自动启用运维。案例文件在 `data/operations/baselines/`；重算基础案例物流使用 `scripts/build_operations_baseline_logistics.py`，加 `--reuse-roads` 复用匹配路网矩阵，否则需要访问 OSRM。

## 5. 实时运行与运维调整

后端持续读取当前时间，执行任务、物料流转和状态保存，查询页面不推进执行。后台约每秒处理一次，进度定期保存，事件与状态转换及时持久化；页面失联时标明估计时间及状态待同步。

实时、今日、7天、4周显示同一份秒级计划，仅改变窗口和刻度。求解范围按依赖及交付影响选择4小时、24小时或7天；超出7天形成4周能力请求，不提供整月分钟级联合最优排程。缺远期需求或日历时明确缺失。

### 5.1 操作闭环

右侧自然语言生成变化草稿，或在参数表单选择环节、对象和变化类型。工时以分钟录入，支持三位小数，接口转为秒，保持单件/整批口径。

即时变化点击“登记并计算”，预约模拟到时生效。候选显示具体资源、顺序、起止时间、路线、交付影响与校验；选定后“应用此计划”。计算与确认期间时钟继续，应用前按最新进度重算校验，新关键变化使旧候选失效。

预计恢复只用于推演，不自动复机；修好后登记“确认恢复可用”，未修好则更新有效估计。已发车任务按实际首次发车时间校验，剩余运输继续；尚未发车却错过时限，或赶不上交接截止，仍拦截。

“更多 → 重开案例”归档本轮，恢复案例参数并映射到当前时间后开始新轮次；旧记录在“运行记录 → 往轮案例”查看。重开模拟不等于确认上一轮故障已修复。

### 5.2 算法与独立校验

运维复用 TS 生产序列内核，结合原顺序、EDD、SPT 等派工，组装按齐套与工位约束安排，配送在已确认批次内修复车辆和路线。原物流求解使用 CCDR-PSO、MO-ALNS 及路网数据；运维修复不等于重新求解所有配送订单。

独立校验器检查任务完整性、能力、前置、日历、重叠、剩余工时、逐时库存、容量、地点连续性、发运、客户窗口及既成事实。候选按加权交付延期、窗口惩罚、改动与完成时间比较；缺成本数据时不评价成本。校验通过表示已知输入下可行，不宣称全局最优或真实现场已执行。

## 6. 智能体与大模型

原生产助手包含排程、异常重排、齐套、交期、方案对比和计划管理六类 Agent，复用编排器、会话、业务事实与确认流程。排程及落库由业务工具完成。

运维 `OperationsAgent` 读取当前活动实例。普通提问、巡检和影响分析默认请求模型，结合工具事实回答；成功显示“AI 回答”和模型名称，失败明确说明原因并展示业务工具结果。Enter发送，Shift+Enter换行。

| 工具 | 作用 | 写入边界 |
|---|---|---|
| `operations.query_state` | 当前任务、资源、暂停/阻塞与预测 | 只读 |
| `operations.analyze_impact` | 已登记事件的依赖、订单和窗口 | 只读 |
| `operations.prepare_event` | 明确对象、参数与单位生成草稿 | 用户核对后登记 |
| `operations.propose_adjustment` | 构造后台候选求解请求 | 用户确认后应用结果 |

自然语言草稿覆盖资源故障/恢复、工序耗时及供给延期，其他变化用表单。模型不直接提交事件或应用方案，不编造资源、工时或全链排程。假设问答不直接登记为现场事件；无待处理变化时不生成当前调整。历史基线计算在方案记录中只读查看。

模型输入时间由程序转为北京时间（+08:00），时长和数量保留数值。运维问答使用简短回答配置，DeepSeek关闭额外思考并限制输出；其他模块默认参数保持。模型调用的超时参数上限30秒，页面等待上限45秒；配置启用不等于调用成功，后端必须有联网权限。

## 7. 数据合同与保存

### 7.1 统一计划

| 对象 | 关键约定 |
|---|---|
| 计划 | `id/name/source/mode/start_at`，订单、资源、任务、库存、供给、路网与运输批次 |
| 订单 | 唯一ID、产品、数量、`due_at`与优先级，交期允许为空 |
| 资源 | 唯一ID、类型、能力、地点、容量与实际日期日历；替代资源须有确认工时 |
| 任务 | 唯一ID、类型、数量、释放时间、前置、候选资源及投入/产出 |
| 工时 | `per_unit/unit_seconds` 或 `batch/duration_seconds`；准备时间另列 `setup_seconds` |
| 物料 | `material_id/location/quantity`；现存与未来供给分开，`@resource`代表随车库存 |
| 路网/批次 | `travel_seconds`以`起点\|终点`为键；`route_groups/routes`绑定装车、配送、返场、车辆及客户顺序 |
| 来源 | `source_ref/source_manifest`、来源指纹与历史版本摘要 |

时间输入为UTC秒或带时区ISO，UTC存储，北京时间展示；无时区日期拒绝。事件分发生、收到和应用时刻，迟报不回滚已提交进度。完整计划输入上限3000任务是保护限制，不代表已验证该规模性能。

默认不允许在制转机，仅明确可转移且提供准备/转运工时的工艺才能改派。客户窗口按来源区分开始服务/完成服务、软窗/硬窗，不随延期自动后移。

### 7.2 参数事件

请求含 `run_id/request_id/type/target_id/data/source/operator/reason`。对象ID从当前实例读取，同一幂等键仅用于同一请求，超时后先查询命令结果。

| type | 对象与 data |
|---|---|
| `resource_unavailable` | 资源；`expected_recovery_at`可空，仅表示预计恢复 |
| `resource_recovered` | 资源；空data，确认恢复 |
| `duration_change` | 生产/组装任务；`resource_id/duration_mode/value`（秒/件或秒/批） |
| `supply_delay` / `supply_quantity` | 未收供给批次；`available_at` / `quantity` |
| `inventory_count` | 已知库位与物料；`location/material_id/quantity` |
| `release_change` | 未开工任务；`release_at` |
| `travel_change` | 已有路段；`from_node/to_node/seconds` |
| `service_change` | 未开工配送任务；`seconds` |
| `window_change` | 未开工配送任务；`window_start/window_end` |
| `order_change` | 订单；`due_at`和/或`priority` |

`source`允许`manual_simulation`和`manual_feedback`；`occurred_at`为发生时间，`scheduled_at`为未来预约模拟。已完成工时和在途既成事实不因参数修改重算。

### 7.3 持久化与历史

| 存储 | 内容 |
|---|---|
| MongoDB `work_orders` | 原生产计划及保存排程 |
| `operations_heads/states` | 活动指针、维护租约与快照 |
| `operations_commands/adjustments/history` | 幂等命令、求解与事件 |
| `operations_runs` | 归档实例 |
| `operations_chain_configs/previews` | 衔接草稿与限时预览 |
| `data/module_history/{production,assembly,delivery}/` | 历史元数据、结果及版本；配送另存独立数据目录 |

先写快照，再按维护者、轮次和版本原子提交活动指针，避免并行推进。活动快照不设过期，替换后的短期快照按策略清理，事件与归档独立保存。备份应同时覆盖数据库、案例与历史文件。

组装评估、配送有效发布后保存独立历史，只有指标时不生成虚假甘特。历史读取不修改当前订单/参数，内容指纹不一致则拒绝复用。物流订单、参数与结果须属同次发布，修改后需重新计算。

## 10. 能力边界与后续开发

- 全链为真实时钟下的模拟，未接入真实MES、设备、GPS或采购平台实时反馈，模拟追赶不是补采现场数据。
- 当前完整案例围绕冰箱工艺。旧QMIX与现行9工序、18工位不完全兼容，历史可查不等于可直接执行；任意组装能力自定义和模型重训待开发。
- 一批次绑定一条保存路线。多产品多级BOM、任意拆批、跨路线自动分配、在途拆批及多级转运尚未完整支持。
- 生产可做同源增量同步；组装和物流新结果须重新选择、预览并明确启用，不自动覆盖旧运行。
- 4周用于观察与能力请求，不宣称整月联合优化；缺输入时不虚构需求、产能、交期或收益。
- 现场上线仍需采集适配、身份权限、工艺安全、质量和审批规则，并用真实数据验收交付、恢复时长与计划稳定性。
