# 产业链运维系统开发计划

日期：2026-11-10。版本：V1.1。状态：首版代码、标准数据与接口已实施，已完成自动化回归及真实时钟接口验收；页面人工交互验收和更大规模生产评估仍待完成。实施清单、实测结果及边界见[首版交付与验收记录](产业链运维系统首版交付与验收记录.md)。

当前标准基线已采用原生产44工序、原组装18工位及原物流保存路线，并显式记录标准关联参数。已保存生产计划可保留原甘特导入，未绑定的下游明确显示缺项；仍不宣称自动汇集各模块当前现场状态。四周层生成能力调整请求，不发布整月细排。见[基线对齐修复记录](产业链运维基线对齐修复记录.md)。

设计依据：[产业链运维系统设计方案](产业链运维系统设计方案.md)。本文把已确认的方向转换为开发顺序、交付物和验收条件。

## 1. 完整性检查结论

总体方向可以进入开发，无需重新调整产品定位。开工前仍有实施细节需要落定，以下已作为本计划的明确任务，而非假设现有系统已经具备。

| 需要补齐的内容 | 本计划的处理决定 | 对应阶段 |
|---|---|---|
| 菜单、路由及页面名称 | 侧边栏和页面标题统一为「产业链运维系统」，沿用统一布局 | P0、P6 |
| 首次启动与真实日期 | 一次性激活已发布计划；无完整前序输入时启用标准计划，固定日期后不随刷新平移 | P0、P2 |
| 参数的数据合同 | 明确对象 ID、单位、单件/批次工时、剩余量、生效区间、来源和版本 | P0 |
| 常驻运行与状态归属 | 新全局实例单一维护方；后台推进、只读查询、可恢复，原局部 MES 不并行推进同一实例 | P3 |
| 中断及恢复语义 | 区分停机、等待、可续做/需重做和实际复机；预计恢复到点不自动恢复 | P3、P4 |
| 求解与运行并发 | 独立求解任务；按最新状态发布未来差异，拒绝过时动作；主时钟持续 | P3、P4 |
| 算法适配与回退 | 先修复共享计算缺口；组装/配送无法使用原模型时采用有约束的确定性回退或明确不可行 | P1、P4 |
| 计划与状态来源 | 前序、标准、模拟反馈、现场反馈分别标记；缺失部分不伪造 | P2、P7 |
| 运行质量与发布证据 | 独立校验、反例回归、端到端对照、延迟与恢复记录 | 全过程、P7 |

尤其要先处理已复现的三个缺口：停机窗口相交判断不足、搜索与甘特时间初始化不一致、未验证硬约束被视作通过。修复前可以做数据、页面和状态开发，但不得开放自动方案发布。

## 2. 固定首版范围

### 2.1 入口与主要交互

| 项目 | 开发要求 |
|---|---|
| 侧边栏标签 | **产业链运维系统**，位于「系统入口」中，与原业务模块并列 |
| 页面标题 | **产业链运维系统** |
| 前端路由 | `/new-ui/home/operations-tools`；Vue 子路由使用 `operations-tools` |
| 后端接口前缀 | `/api/operations-tools` |
| 默认进入 | 读取服务器当前时间、当前全局实例及已激活计划，订阅状态变化 |
| 页面功能区 | 实时总览、事件与反馈、调整方案、计划与复盘；计划初始化放在管理操作中 |
| 主时钟 | 服务器当前时间，UTC 存储、北京时间显示、1∶1；无主时钟暂停/倍率控制 |

用户主要路径为：打开当前状态 → 从资源/任务登记变化 → 即时看到影响 → 后台生成具体计划 → 查看差异和校验 → 应用仍有效的未来调整。无活动实例时显示未启用及初始化入口，不在每次打开页面时生成新任务。

### 2.2 首版必须具备

- 生产、物料、组装、配送共享一个运行实例、业务时间及上下游数量关系。
- 已排定标准计划能在真实时钟下持续执行，页面关闭不影响后台运行。
- 参数落到具体工单工序、物料批次、组装工位、配送任务与路段。
- 支持耗时、资源可用性、数量、预计就绪/窗口四类输入模板；订单变更使用明确的业务变更记录。
- 事件即时生效；生产/组装/运输按约束推进，受限任务等待，其他任务继续。
- 近端滚动与跨环节影响传播，输出明确顺序、资源、起止及车辆路线。
- 人工选择应用、独立校验、版本核对、事件追溯和结果对照。
- AI 调用相同工具组织建议；LLM 不可用时仍能人工录入、规则计算和执行。

首版不扩展到维修工程师/工具/备件联合调度或售后服务系统。人员、能源、质量先反映为已确认的工时、可用区间或可用数量变化。已有订单、生产、组装、物流入口继续保留。

### 2.3 多层时间粒度的交付边界

| 层级 | 首版要做到的事情 |
|---|---|
| 即时执行 | 事件时间保留到秒，直接处理当前任务和资源状态，不等待 AI/优化 |
| 近端 | 默认未来 4 小时，必要时至当班/24 小时；按工序和路线节点生成分钟级具体安排 |
| 7 天 | 传播供给、批次与运力影响，数据完整时生成跨班次调整；不完整时显示缺口和待补数据 |
| 4 周 | 展示已有日/周能力需求，提出超出短期窗口的调整请求；不新增整月分钟级联合求解器 |

窗口、检查周期及求解预算可配置。没有远期订单就显示需求未给定，不生成虚构负荷。

## 3. P0：锁定数据合同与运行规则

**目标：**让前序计划、标准计划、事件和所有求解器使用同一套对象与单位。

交付以下内容：

1. 统一计划结构：来源与版本、实际日期、订单/批次、任务、工艺前置、投入产出、资源、供给、路线、原承诺及初始截面。
2. 参数目录：业务对象、允许字段、数据类型、单位、单件/批次口径、有效区间、可编辑范围、确认要求。
3. 状态与事件规则：待执行、执行中、阻塞/中断、完成、取消；资产可用/不可用；真实反馈与预计状态分开。
4. 统一目标：按订单交付完成计算延期，固定比较顺序为硬约束、加权延期、额外成本和计划改动。原生产交期是内部约束，不能默认等同于客户交付承诺；缺失成本显示未评估，不能当零成本。
5. 每个来源的主键与单位映射、计划生效规则、数据缺失时的拒绝或回退条件。

关键约定：

- 关联必须是订单→生产工序→产出批次→组装任务→成品→配送，不能以名称关键词代替正式关系。
- 工时可以按件或按批次；不同机台/工位的有效工时单独表达。备用资源没有已确认工时或能力时不产生可应用的改派建议。
- 库存分清现存、有效预留、隔离与在途；预计供给和实际收货分别记录，数量守恒。
- 订单、任务、资源和事件使用稳定 ID；人工补录发生时刻不回拨主时钟。
- 首版每个部署指定一个活动全局实例，历史实例保留；同一现场对象指定一种权威反馈来源。

**完成条件：**标准计划和生产导入能够使用相同结构表达；每个首版参数有明确的计算位置及校验规则。无关键业务参数依赖 AI 临时编造。

## 4. P1：修复排程计算基础，建立独立校验

### 4.1 前置修复

| 已发现问题 | 开发工作 | 必须通过的反例 |
|---|---|---|
| 开始时刻避开停机，作业仍可能跨停机 | 用完整有效加工区间判断相交，计算足够容纳作业的可用区间；有中断时按分段规则处理 | 作业 `[0,4)` 与停机 `[2,3)` 不能作为连续加工通过 |
| 搜索评分与最终甘特时间口径不同 | 统一工单释放、机台初始可用、停机、替代资源和逐资源工时的解码逻辑，搜索、输出、指标共用一致规则 | 到达 10、机台可用 12、工时 4：有效结束均为 16 |
| 未校验硬约束仍算合法 | 引入通过/违反/未验证，必要约束未验证则不可发布；推荐说明匹配实际覆盖 | A 前置于 B，B 却先执行：拒绝；缺必要验证数据：未验证 |

不能只在 UI 修改工时字段，而解码器仍读取旧的统一 `duration`。逐资源工时适配需贯通搜索评价、甘特、剩余任务和指标，同时兼容原单一工时输入。

### 4.2 独立校验器

校验器读取冻结输入、当前事实和候选明细，自行计算，不复用“候选自称可行”的标志。至少覆盖任务完整性、工序前置及工时、资源能力与占用、停机、物料及数量、组装就绪、装车、容量、路线时间、硬时间窗和冻结事实。

输出逐项结果、对象、实际值、要求值和原因。正在中断的工序累计有效加工时间，暂停不算加工；资源占机与实际加工分开校验。

**完成条件：**上述反例和原故障重排、策略、普通 APS 回归通过；每个必要硬约束可验证或明确阻断发布。现有针对性测试曾有 12 项通过，但不作为本阶段完成的替代证据。

补充空剩余任务、单工序、单机/单车、无替代资源和持续不可用等边界用例：返回合法的完成/等待/不可行结果，不抛出未处理异常，也不推荐空甘特作为成功方案。

## 5. P2：标准计划与前序计划读取

### 5.1 标准计划交付物

已在 `data/operations/standard/` 保存首版计划数据、来源说明和参数变化示例，并实现加载、校验和一次性激活；新增或扩大算例时继续遵循下述要求。

标准种子至少包含两类产品、多个订单，生产与组装的前置和资源竞争、可用替代资源、两辆车及客户时间窗，并有一项供给约束。任务规模以能够核算、能够暴露跨环节影响为准，不限制用户场景数量。

必须提供：

- 订单、物料/BOM、工艺、产出关系、资源能力、日历、固定路网时间矩阵和完整排程。
- 一个正常可行基线，以及工序变慢、机台停用、到货延迟、工位不可用、车辆缺失、路段延迟的参数变化用例；均指向同一任务世界。
- 日期激活配置、来源标记和初始执行截面；短期批次/长期能力数据按实际提供范围表达。
- 输入校验、基线可行性及设计方案第 7 节排程例子的可复核结果。

首次启用时确认生效日期和时刻，可选即将开始的任务集。若覆盖过去时段，必须有初始截面或明确的标准模拟回放。之后刷新、重开、跨日均不重新平移计划、不重复创建相同订单。

### 5.2 前序接入顺序

| 来源 | 本阶段处理 | 不能直接使用时 |
|---|---|---|
| 生产计划 | 优先实现按 plan/solver/version 只读导入任务和甘特，确认日期、资源和产出映射 | 展示具体缺项，保留完整标准计划 |
| 物料与就绪 | 导入目录、供给与库存副本，建立严格批次/用量/就绪关系 | 不把整单关键词映射当作实时齐套，使用标准来源并标记 |
| 组装 | 读取选定评估结果，将产品/作业/工位索引绑定订单批次，标定单位 | 使用标准组装计划，后续补适配 |
| 配送 | 读取选定车辆路线和节点时间，转换日期，关联成品批次 | 使用标准配送计划，后续补适配 |
| 订单产运 | 接选定版本的需求与节点、时间承诺，保留参考层标记 | 暂不作为执行指令 |

替换任一标准片段时重验上下游数量、时间和资源，用户可查看来源及变更；不能把互不相关的历史甘特拼接。不得调用旧 `start_from_package` 来导入新实例，因为它会写旧计划并启动原 MES。

**完成条件：**标准计划可独立启用；生产来源能预览、校验并在映射成立时导入。组装/配送接入进度不阻塞标准模式，但缺口不能隐藏。

## 6. P3：后台常驻运行、状态存储与接口

### 6.1 执行服务

开发独立于原 `production_execution.active` 的全局运行服务。所有任务共用服务器当前时间，事件处理推进生产、组装、库存和运输，按约束产生可开工、完工、到达、阻塞与恢复状态。

实现要求：

1. 单一活动实例指针；每个实例一个有效执行维护者，使用持久化认领/租约，提交时核对维护者代次，防止租约失效的旧进程与新进程同时推进。
2. 事件落库后按稳定顺序处理，同一时刻先处理阻断事实，再处理释放/完成，最后判断可开工；边界规则写入测试。
3. 处理故障时立即限制相关任务，保留实际进度；其他任务继续，等待时间进入时长和风险，主时钟不暂停。
4. 预计完成和实际/模拟反馈分开；标准模式按规则产生明确的模拟反馈，在线对象依赖指定现场来源。故障机台不会因预计恢复到点而自动可用。
5. 关闭页面仍运行；重启恢复检查点及事件游标，去重消费。当前时间继续走，状态尚未补齐时显示恢复中/过期，不伪称已同步。
6. 全部任务完成后等待新任务，时间继续；无意图明确的新计划不得重复执行旧订单。

测试可以注入时钟，正式接口不允许修改服务器时间、主时钟倍率或回拨。资源/任务暂停与主时钟继续是不同状态。

### 6.2 持久化与发布协议

新增数据按 `operations_*` 命名，至少覆盖计划版本、运行/状态版本、事件与命令、候选与校验、发布与审计。具体可按聚合存储，不要求每个业务对象单独一张集合。

首版采用**单实例写入协调＋不可变状态版本＋单文档 CAS 切换已提交版本指针**的协议：先准备完整新状态，再核对当前版本并切换可见指针；查询只读已提交状态。事件/命令有唯一幂等键，故障恢复能够识别已提交、待重试和无效准备数据。大计划、日志不无限追加到同一个 MongoDB 文档。

不得依赖当前部署天然支持跨集合事务。P3 必须验证提交前、准备后、指针切换后进程退出的恢复行为；若实现改用多文档事务，需同时给出满足条件的部署方式及验证结果。

### 6.3 最小接口合同

以下为拟开发接口，不表示已存在：

| 接口 | 用途 |
|---|---|
| `GET /current` | 服务器时间、活动实例、计划来源、已提交状态版本、最后同步时刻及分环节状态 |
| `GET /stream` | SSE 事件流，带可重连游标与心跳；只读，不推进业务 |
| `POST /plans/preview` | 读取标准/前序输入、转换、校验及缺项预览 |
| `POST /plans/activate` | 一次性启用已确认计划，带请求幂等键和预期版本 |
| `POST /events` | 登记故障、恢复及参数反馈；返回事件 ID、接收状态与当前状态版本 |
| `POST /adjustments` | 提交后台重排任务，立即返回任务 ID，计算不阻塞执行 |
| `GET /adjustments/{id}` | 任务状态、输入版本、具体候选、校验、差异及解释 |
| `POST /adjustments/{id}/apply` | 按当前时刻及相关对象版本校验，只提交未来有效差异 |
| `GET /history` | 查询事件、计划修订、执行和发布记录，支持对照复盘 |

所有路径均加 `/api/operations-tools` 前缀；写入记录操作者、来源及原因。重复提交返回已处理结果；409 表示状态/版本冲突，422 表示输入或必需条件不满足，不能返回假成功。故障事实可以导致计划不可行，应先登记事实再报告阻塞，不因当前计划会冲突而拒绝真实反馈。

**完成条件：**不打开页面也会推进；读请求无业务副作用；订阅补齐不漏事件；重启和重复命令不重复派工、扣料、产出或收货。

## 7. P4：事件录入、分层重排与安全接回

### 7.1 统一事件入口

四类输入模板共用对象选择和参数目录，自动带出运行实例、资源/任务、原值及当前时间。确认新值、生效范围、来源和预计恢复等信息后，先即时更新状态，再异步评估未来影响。

一期实现人工输入与模拟事件；后续现场接口调用同一事件入口。取消/更正通过新记录关联原事件，不删除已发生事实；多条变化可以作为一组提交并给出关联影响。预计恢复未知时允许登记，但推演需提供已确认估计或明确返回无法计算。

### 7.2 调度与回退策略

| 环节 | 首版实现 | 限制与回退 |
|---|---|---|
| 生产 | 修复后的 TS 主搜索，EDD 交付候选，SPT 快速基准；GA 按预算补充 | 传入剩余任务、释放、停机、能力及逐资源工时；全部独立校验，无合法结果保持可执行部分并报告阻塞 |
| 组装 | 先实现按齐套、前置、工位能力和占用的确定性可行排程；适用时接入 QMIX 候选比较 | 验证模型输入维度、产品数量、工时单位及共享限制；超出范围不直接套模型，不在页面触发重新训练 |
| 配送 | 先实现可校验的原路线修复/改派，再接已有路径算法的单次有限预算求解 | 输入成品就绪、车辆位置/载荷、已访问站点和时窗；不调用原多轮实验全流程阻塞即时运行 |

所有确定性回退也必须校验，不以“规则”名义跳过约束。标准计划使用固定、有来源的路网矩阵，不依赖临时外网查询；真实路况接入失败则保留最近有效数据并标记时效，缺必要时间不能假定为零。

逐资源工时、组装作业类型与产品批次、车辆全局参数与实际有效资源，都要通过适配器进入计算。共享配置按任务隔离，求解副本不修改原模块数据、全局 CFG 或其他实例；独立进程隔离 CPU 计算、随机种子和模型状态。

### 7.3 影响范围和候选协调

从当前时刻、受影响资源、持续时间、任务依赖、缓冲及承诺选择窗口：默认 4 小时，必要时当班/24 小时，再升级至 7 天；4 周层输出能力缺口及前序调整请求。

只重排受影响任务及必要竞争任务。每层最多保留 3 个候选作为初始配置，完整链最多 27 项；局部变化不必展开整链。发生跨层冲突时反馈前序，超预算则报告搜索范围和剩余风险。不得在窗口末端截掉未解决影响。

输出每项任务的资源、顺序、起止、数量，每辆车的装载、路线、到达/服务和返场，以及订单延期、额外成本、改动范围、约束报告。大模型返回的文本不作为计划本体。

### 7.4 持续时钟下应用

求解读取快照，执行继续。等待用户确认期间任务和车辆可能已推进；发布时重新计算实际可变范围，依赖失效则修订或重算，不能简单平移整张甘特。

应用只提交未来有效差异，相关对象版本核对与发布走 P3 提交协议。不因无关心跳或无关事件废弃全部候选；新关键故障使相关候选失效。过时动作、重复应用、库存被占、资源已开工均给出可解释结果。无新方案时，未受限任务继续，受限任务等待，主时钟不停。

**完成条件：**至少完成生产变慢、供给延迟、组装受限、车辆缺失和一项跨环节组合变化的具体排程闭环；求解超时、确认过晚及并发新事件均不破坏当前运行。

## 8. P5：AI 工具接入与价值验证

复用现有工具注册与 Harness，在新模块注册状态查询、事件解释、影响分析、参数建议、候选生成和结果对比工具。先实现可直接调用的业务工具，再接自然语言，不因 LLM 不可用阻塞 P3/P4。

AI 负责对象关联、缺项提示、参数依据、工具编排及解释。结构化参数来自同一目录；“M1 变慢”缺具体工时或有效观测时要求补充，不凭空生成 9 分钟。自然语言识别结果进入可核对表单，实际提交仍走统一事件入口。

一期由用户选择方案并应用。取证和候选推演不产生实际派工；库存、任务状态、原承诺和发布结果不能由对话文字改写。UI 的应用操作调用相同发布服务，不绕开校验。

记录证据、工具轨迹、失败与人工修正，对比“不调整”“规则/人工工具”“AI 辅助同一工具”。同一算法产生相同计划时，AI 的收益以操作耗时、遗漏和修正量评价，不归功为额外算法优化。

**完成条件：**AI 能返回指向具体候选的解释；断开 LLM、工具超时、输入不完整时，录入、规则排程和当前运行仍可使用。

## 9. P6：页面及侧边栏交付

在 `HubLayout.vue` 的「系统入口」增加 **产业链运维系统**，新路由沿用现有布局与样式。入口不依赖组装或物流嵌入服务在线才可用，因为标准模式应能独立运行。

| 页面区域 | 具体功能 |
|---|---|
| 实时总览 | 服务器时钟、实例/计划来源、同步状态、生产/物料/组装/配送进度，订单交付风险和当前阻塞 |
| 事件与反馈 | 从实际对象发起四类表单，记录故障/恢复、发生时刻与来源，显示处理结果 |
| 调整方案 | 计算状态、明确资源/顺序/时间/路线、依据、逐项校验及未评估范围 |
| 计划与复盘 | 标准启用/前序导入管理、版本、实际/预计差异、事件和方案对照 |

进入时先取快照，再订阅游标之后的 SSE；显示时钟定期与服务器校准。断线显示最后可信状态与时间，自动补齐或重读快照，不能把旧状态继续标为在线。页面交互与路由切换不停止后台执行。

按钮需区分“事件已接受”“调整计算中”“待选择”“已过期需重评”“应用成功/失败”。禁止让“计算中”表现为全系统暂停；未通过必要硬约束的候选不能应用。原模块导航携带计划/实例上下文，未接入共享状态的旧页面明确显示其独立模式。

**完成条件：**菜单和标题严格使用用户指定名称；首次无实例、正常运行、故障、求解、延迟确认、断线重连和无合法方案均有完整操作路径。

## 10. P7：联合验收与运行交付

### 10.1 验证清单

| 检查组 | 必须验证的内容 |
|---|---|
| 计算与校验 | P1 三个反例；单件/批次口径、不同资源工时、工序漏排、停机相交、物料守恒、组装共享、装载和路线时间 |
| 连续执行 | 页面关闭后任务继续；重开时实例和计划日期不变；待确认不暂停；无关任务在故障期间继续 |
| 多层时间 | 短时故障留在近端，跨班次升级，长期缺口形成请求；各层占用和数量不重复 |
| 实际与预测 | 预计恢复到点未复机继续阻塞；实际反馈改变进度，模拟来源始终可辨；不能只按时间将受限任务标为完成 |
| 并发与恢复 | 重复/乱序/迟到消息，双执行者，提交中断，服务重启，SSE 重连，已过开始时间的候选 |
| 算法与 AI 失败 | 求解超时/异常、无解、模型不适用、路况不可用、LLM 不可用时，有明确回退及残余风险 |
| 回归 | 原 APS、生产看板、动态重排、组装和配送入口保持可用，新增状态不改写原 active/库存 |

单元/集成测试用可控测试时钟快速推进；至少一轮端到端验收使用服务器真实时间验证关闭页面、异步求解和确认期间的连续性，不以快进测试替代。

### 10.2 算法和性能证据

小模型用穷举/精确基准对照，复核设计方案中的三订单例子；标准算例和代表性运行场景固定输入、参数及多组种子，记录可行率、相对目标差距、耗时和波动。算法内部评分、返回甘特和统一报告须一致。

性能报告写明机器环境、订单/工序/车辆规模、反馈频率及计算预算。分别量测事件接收到状态提交、页面可见、候选生成和应用的耗时。主动注入慢求解，验证执行处理与时钟仍继续；未实测前不声明“秒级全部场景”或固定提升比例。

### 10.3 部署和回退

提供启动/停止执行服务、求解工作进程、初始化标准计划、备份/恢复与问题排查说明；在 FastAPI 生命周期中管理服务启停，并处理进程退出及重新认领。

新增模块可单独停用，停用状态明确展示，状态和审计保留；不能通过删除数据或重置旧 MES 作为回退。共享计算修复保留原输入兼容及回归证据。部署文档说明 MongoDB 提交协议、只允许一个维护者的运行约束、真实时间和模拟/现场来源边界。

**完成条件：**交付可运行数据包、测试记录、算法/性能报告、操作及部署说明；所有必要约束通过，未支持项和现场接口缺口明确列出，才能将首版标记完成。
