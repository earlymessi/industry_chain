# 产业链运维系统接口与数据约定

2026-11-10，首版。所有执行数据位于独立的 `operations_*` 集合，不写原生产看板的 active 实例或原库存。

## 1. 时间和来源

- 主时钟为后端 `time.time()`。UTC 秒数或带时区 ISO 时间输入，UTC 存储，北京时间显示。无时区时间字符串拒绝。
- 首次启用固定实际日期，刷新不平移计划。后台约每秒处理一次，状态进度最长约五秒检查点一次；发生状态转换或提交事件时立即持久化。页面显示服务器时间，失联时明确标记时间估计与状态待同步。
- 首版仅激活 `mode=simulation`。标准执行器根据已确认参数产生模拟进度、到货及完成反馈；这些不是 MES、设备或 GPS 实测。人工确认反馈仍属于当前模拟实例。
- 事件发生、收到、应用时刻分开记录。迟报不回滚已经提交的进度，影响从可确认截面向后传播。
- 预计维修恢复只用于候选计算；必须登记 `resource_recovered` 才改变实际可用状态。

## 2. 统一计划

2026-11-11新增「计划衔接」：选择前序来源、确认部件/BOM/数量、统一时间映射、补充资源化交接任务并预览全链路。步骤、接口、来源兼容与范围见[计划衔接实施记录](产业链计划衔接实施记录.md)。当前已保存生产同步与新链路建立是两个操作：同源同步保留运行进度，新链路需明确归档并启用。

生产默认从数据库 `work_orders` 中选择已保存的排程与算法结果，不固定某个计划ID。首次启用必须选择来源；不自动启用固定标准计划。`production_source.json` 和 `binding.json` 仅用于明确选择「演示基线（备用）」时构建跨环节示例；组装工艺直接读取 `MASA-QMIX/utils/production_line.py`，物料读取原集成目录。`prepare_standard(start_at)` 固定实际日期并校验完整关联。原独立 `refrigerator.json` 已退出运行，仅将小算例保留为测试夹具。

| 对象 | 必需内容与语义 |
|---|---|
| 计划 | `id/name/source/mode/start_at/orders/resources/tasks/stock/supplies/travel_seconds/route_groups/routes`；来源说明写 `provenance` |
| 订单 | 稳定 `id/name`、产品、数量、实际 `due_at`、正数优先级；订单最终交付数量须守恒 |
| 资源 | `id/name/kind/capacity/location/working_windows`；kind 为 production、assembly、vehicle；日历为实际时间区间 |
| 任务 | `id/name/kind/quantity/release_at/duration_mode/alternatives`；业务任务绑定 `order_id`；工艺用 `predecessors` 和必要 `transfer_seconds` |
| 工时 | `per_unit` 使用各候选资源的 `unit_seconds`；`batch` 使用 `duration_seconds`；另列 `setup_seconds`。不同资源没有有效工时，不可凭空改派 |
| 在制转移 | 只有 `resumable=true` 才允许已投入任务换资源；`transfer_on_reassign_seconds` 计入必要转移/准备。工艺是否能转机需业务确认 |
| 投入产出 | `inputs/outputs` 每行含 `material_id/location/quantity`。工单产出、组装消耗、成品装载必须明确相连；`@resource` 表示当前车辆库存 |
| 现存 | `stock` 为库位×物料数量；初始截面不得重复键。首版没有独立质量隔离、批次保质期或财务计价模型，输入须为可用数量 |
| 供给 | `supplies` 使用批次 `id`、物料、库位、数量和实际日期 `available_at`；标准模拟按该时间生成一次到货反馈 |
| 路网 | `travel_seconds` 的键为 `起点|终点`，值为秒。方向单独表达，无路径不补造时间 |
| 运输批次 | `route_groups` 绑定 loading_task、delivery_tasks、return_task、depot、vehicle_options；`routes` 给出 vehicle_id 和 stops |
| 配送任务 | `to_node/service_seconds/window_start/window_end`；客户承诺用于延期评价，收货窗口是硬约束，二者不同 |

完整计划最多 3000 项任务是输入保护上限，不是该规模已通过性能验证的声明。必须满足唯一 ID、无环前置、有效资源与日期、订单交付数量、装载投入产出数量、车容量及完整路线校验。仅通过语法检查还不能激活，须生成基线并经过独立排程校验。

已保存生产计划可从来源列表选择并导入未开工的执行副本，保留选定算法的原甘特、原工序和设备允许集合，显式确认原时间单位。工时不加任意替代系数，在制默认不允许转机。缺失BOM、客户承诺、组装或配送关联时按 coverage 标记，不虚构下游。scope=production 使用完成工序作为工单目标，不把生产完工当成客户交付。历史起点只在确认模拟回放后允许；不接管旧MES的在制截面。

due_at 可为 null，缺承诺的订单显示交期待确认，不把自动估算的生产交期当成客户承诺。各来源对象带 source_ref，计划保存 source_manifest 与源数据指纹；生产预览返回 source_version，启用时重新读取并检查变化。原生产工时默认小时，与原界面一致；分钟/秒来源须显式选择。

### 库内生产计划持续同步

页面「生产来源」选择计划及其已保存算法；每15秒检查绑定来源指纹，有变化显示「库内有更新」，由用户预览并确认同步。后台不会自动用新排程覆盖现场安排。

- `production_link` 保存所选 `plan_id/solver_id/time_unit/anchor_at/source_version/synced_at`。原计划日期及运行实例ID保持，时钟继续。同步不向原生产模块反向写入。
- 同一来源、同一组唯一工单/工序与前置关系才可原位同步。未开工工序可以接收已保存甘特、允许设备集合、工时、数量、开工约束及优先级/交期；已开工、已完成和已经消耗投入的任务冻结，不追溯修改实际进度。
- 参数采用「上次来源快照、当前运维值、新来源值」三方比较：来源未变则保留本地修改；仅来源改变则采用新值；两边对同一字段产生不同修改则提示冲突，不能静默覆盖。库存与故障/恢复状态不因同步复位。
- 保存的源甘特先独立校验；合并后按当前进度重新校验资源、工艺、投入产出、路线和既成事实。已有的组装、配送关联保留，受影响的后续时刻参与全局校验；不为任意新计划猜造下游关系。
- 源无变化只登记绑定检查，不恢复原甘特或抹掉运维调整。预览有效期5分钟；确认时重读数据库和当前进度。源指纹或运行约束版本变化返回409，要求重新预览。
- 另一份计划、工序增删/改名或工艺结构变化不能直接继承旧进度；页面提供「归档当前运行并启用」。用户明确确认后保留旧实例及事件，再从当前时钟启用新副本。不同工单不会伪装成原批次的连续执行。

运输窗口沿用来源口径：window_policy=service_start 表示最迟开始服务，默认约束服务完成；window_hard=false 保留原物流软窗及惩罚权重，允许迟到但记录并计入候选排序；默认硬窗仍拒绝越界。已发生开始服务时间单独保留，途中故障不会凭空补成按时到达。原物流窗口不能被误称为客户交付承诺。

## 3. 参数事件

统一请求示例，先 GET `/current` 获取 `run_id`：

```json
{
  "run_id": "当前实例ID",
  "request_id": "客户端生成的唯一幂等键",
  "type": "duration_change",
  "target_id": "O-A-T1",
  "data": {"resource_id": "M1", "duration_mode": "per_unit", "value": 180},
  "source": "manual_simulation",
  "operator": "操作人员",
  "reason": "该产品在M1的确认加工时间调整为3分钟/件"
}
```

| 变化 | target_id | data |
|---|---|---|
| resource_unavailable | 机台/工位/车辆 ID | expected_recovery_at，可为 null；实际仍不可用 |
| resource_recovered | 资源 ID | 空对象；表示确认恢复 |
| duration_change | 具体生产/组装任务 ID | resource_id、duration_mode、value，单位秒/件或秒/批，保持原任务口径 |
| supply_delay | 未收到的供给批次 ID | available_at，新的预计供给日期 |
| supply_quantity | 未收到的供给批次 ID | quantity，新的确认数量 |
| inventory_count | 库位与物料的稳定标识 | location、material_id、quantity；修正已有项，不凭空创建物料 |
| release_change | 尚未开工任务 ID | release_at |
| travel_change | 已有路段标识 | from_node、to_node、seconds；已在途行驶段保留既成进度，未来路段按新值计算 |
| service_change | 尚未开工配送任务 ID | seconds |
| window_change | 尚未开工配送任务 ID | window_start、window_end |
| order_change | 订单 ID | due_at 和/或 priority；初始承诺另存，变更留痕 |

界面以分钟输入工时，再转换成秒。已完成加工不被新工时重算，单件任务只修正剩余数量的有效工时。数量模板用于库存和未收供给，首版不支持随意改订单数量、工艺或拆分已经装车的批次。

`source` 仅允许 manual_simulation、manual_feedback。可附实际 `occurred_at`；预约模拟使用未来 `scheduled_at`，不会阻塞其他即时命令。预约不能标为已经发生的人工确认反馈。当前参数变化示例见 `data/operations/standard/events.json`，全部指向具备来源映射的原设备、工位、物料和车辆。

## 4. REST / SSE

统一前缀 `/api/operations-tools`。

| 方法及路径 | 用途 |
|---|---|
| GET /current | 当前实例、服务器时间、健康状态、参数目录、四层窗口；只读，不推进执行 |
| GET /stream | SSE 首次及版本变化发送 snapshot，其他时间 heartbeat；重连获取当前完整快照 |
| GET /plans/sources | 仅列出库内具有已保存甘特的生产计划、可用算法和工单数 |
| GET /plans/production/status | 绑定来源、当前/最新指纹、是否有更新；来源缺失保留当前运行并提示 |
| POST /plans/production/preview-sync | run_id、plan_id、solver_id、time_unit；返回差异计数、校验与5分钟preview_id；不满足原位同步条件返回new_run模式 |
| POST /plans/production/sync | run_id、preview_id、request_id；重读并校验后同步未开工部分 |
| POST /plans/preview | 标准计划、完整 JSON 或生产来源预览；返回可激活条件/缺项 |
| POST /plans/activate | 必须明确生产/演示/JSON来源，或source=chain及有效preview_id；切换生产或衔接计划须confirm_new_run=true及匹配previous_run_id，旧实例完整归档 |
| POST /events | 登记即时事件或预约模拟，返回命令 ID |
| GET /commands/{id} | 命令提交结果或排队状态 |
| POST /adjustments | run_id + 可选 request_id，启动后台独立求解 |
| GET /adjustments/{id} | 求解状态、候选明细、约束校验、当前是否过期 |
| POST /adjustments/{id}/apply | run_id、candidate_id、request_id、operator，重校验后应用 |
| GET /history | 当前实例事件和调整记录，默认最近100条，可指定 limit，最大500 |
| POST /assistant | message、可选 use_llm；工具事实、草稿、调用轨迹或候选请求 |

执行命令返回 200/done 或 202/queued；业务数据不合法返回 422，实例/约束版本冲突、服务停用或重复应用返回 409。幂等键相同且请求相同返回原结果，不同请求复用相同键拒绝。网络超时后应查询原命令，不应把超时当作一定未提交。

旧独立示例 REFRIGERATOR-STANDARD-v1 仍可通过 replace_legacy=true + previous_run_id，完整归档后切换 alignment_version=2 基线。其他活动计划只可按上述生产同步或明确确认的新运行切换流程处理，不能直接覆盖。旧事件不改名冒充原设备反馈，主时钟不回拨。

候选按加权交付延期、改动量、完成时间排序，成本没有导入则明确未评估。求解超时/无解不修改执行计划。应用时读取当前进度，保留完成与在途事实，并对剩余安排重新计算及独立校验；新的关键事件使旧候选失效。

窗口默认4小时，按影响扩展24小时/7天。优化候选保留窗口外已排任务及物料预留，跨界冲突须扩大窗口后再算。超7天的变化生成4周能力请求，首版不给整月分钟级排程。没有后续需求就展示未给定。

## 5. 存储与运行约定

`operations_heads` 是原子活动指针及维护者租约；`operations_states` 是不可变快照；`operations_commands` 是幂等命令；`operations_adjustments` 是求解快照与结果；`operations_history` 保存事件；完成实例归档到 `operations_runs`。活动快照不设过期，已被替换的进度快照保留两天后清理；事件和实例归档不随短期快照 TTL 清理。需按持续运行频率规划磁盘容量与备份。

MongoDB 单机也可运行：先写快照，再以 owner/epoch/version/lease 条件原子提交活动指针，只有取得维护权的进程能提交；丢失维护权的旧进程不把尚未提交的命令误标为业务失败。启动时补齐命令回执和事件记录。双进程部署仍建议仅一个 Uvicorn worker，避免无意义的重复服务与求解。

停机期间没有现场采集。恢复后模拟执行器从最后检查点追赶到当前时间；不是补采了真实设备数据。服务器时钟回拨时状态不倒退并给出警告。现场上线仍需适配真实反馈与数据质量、身份权限、工艺安全规则和业务审批。
